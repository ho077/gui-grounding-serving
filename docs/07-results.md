```
模型    Qwen2.5-VL-3B-Instruct
数据    ScreenSpot 1272 条（mobile 502 / web 436 / desktop 334）
坐标口径 --coord-space pixel（基座原生输出绝对像素，实测确认，见 6.1 节）
```

| 档位 | 样本 | 准确率 | 准确率(保守) | 解析失败/拒答 | 偏移 p50 | 偏移 p90 |
|---|---:|---:|---:|---:|---:|---:|
| bf16_zero_shot | 1257 | **80.0%** | 79.0% | 0 / 15 | 24.4 px | 338.5 px |

**按平台**

| 平台 | 样本 | 准确率 | 偏移 p50 |
|---|---:|---:|---:|
| mobile | 496 | 85.1% | 25.6 px |
| web | 435 | 76.1% | 22.8 px |
| desktop | 326 | 77.3% | 23.2 px |

**按指令类型**

| 类型 | 样本 | 准确率 | 偏移 p50 |
|---|---:|---:|---:|
| text | 696 | 88.9% | 27.9 px |
| icon | 561 | **68.8%** | 18.8 px |

**按目标面积**

| 面积档 | 样本 | 准确率 | 偏移 p50 |
|---|---:|---:|---:|
| s (0.5k–2k px²) | 48 | 62.5% | 10.7 px |
| m (2k–8k) | 279 | 60.2% | 15.2 px |
| l (>8k) | 929 | 86.9% | 27.7 px |

**这组数字的三个意义**：

1. **对齐公开锚点**：GUI-Actor 报 Qwen2.5-VL-3B 在 ScreenSpot 上 80.9，本机 80.0。
   差 0.9 个点，说明评测链路可信 —— 这是整个项目唯一的外部校准点。
2. **小目标确实是短板**：面积 <8k px² 的两档只有 60~63%，而 >8k 有 86.9%。
   量化只会让这个落差更大，所以后续必须按面积分层看，不能只看总准确率。
3. **图标比文字难**：icon 68.8% vs text 88.9%，差 20 个点。

## 2. LoRA 微调：一例失败实验（负面结果）

### 2.1 配置与结果

```
基座    Qwen2.5-VL-3B-Instruct
数据    ShowUI-desktop 303 条（101 张图 × 最多 3 个元素）
LoRA    rank 32 / alpha 64 / target=all，冻结视觉塔，投影层可训
训练    2 epoch、有效 batch 16、lr 1e-4、38 步、19 分钟、loss 0.875→0.66（均值 0.723）
```

训练**机械上完全成功**（adapter 240MB，checkpoint 正常落盘，格式输出 100% 可解析），
但**精度崩了**：

| 模型 | 坐标口径 | 准确率 | 对照 |
|---|---|---:|---|
| 零样本基座 | pixel | **80.0%** | — |
| SFT 后 | norm（[0,1000]） | 9.8% | 61 条分层抽样 |
| SFT 后 | pixel | 24.6% | 同一批样本 |

SFT 确实学会了 `[0,1000]` 归一化输出（训练目标就是这么写的），
但定位精度掉了 3~8 倍，**连它的训练分布 desktop 也只有 25~37%**（零样本 desktop 是 77.3%）。
所以不是"换了个坐标口径导致评测错"，而是模型本身退化了。

### 2.2 第一轮根因（后来被修正）：数据量只用到了 4%

排查顺序（重要：没查清前不要归因给"模型不行"）：

1. 先验数据：坐标是否越界 —— 0 条越界，数据干净
2. 再验预处理：`preprocessor_config.json` 的 `max_pixels` 是否被改成训练时的值 —— 与基座一致
3. 最后查数据规模 —— 脚本只读元数据 JSON，产出 303 条

> **修正（第二轮才看清）**：最初我把"parquet 有 7496 条"理解成"少了 7000 张图"，
> **这个判断是错的**。7496 是**元素数**，ShowUI-desktop-8K 实际只有 **101 张桌面截图**
> （每张约 74 个元素），元数据 JSON 覆盖的也是同样的 101 张，并不"少"。
> 真正的限制是 `max_per_image=3`：101 张 × 3 = 303 条。
>
> 顺带修掉一个隐蔽 bug：`per_img` 原按 `image_url` 去重，而不同 parquet 里存在同名
> `screenshots/message/screen_1.png`，会把不同的图当成同一张（1600 条被压回 303 条），
> 落盘时还会互相覆盖。已改为按**图像内容哈希**去重。

### 2.3 三轮微调的实测

| 版本 | 数据 | 训练目标 | 超参 | 准确率（原分辨率） | 偏移 p50 |
|---|---|---|---|---:|---:|
| 零样本基座 | — | — | — | **80.0%** | 24.4 px |
| SFT v1 | 303 条 | [0,1000] | lr 1e-4 / rank 32 / 2 epoch | 9.8%~24.6%¹ | — |
| SFT v2 | 1600 条 | [0,1000] | lr 2e-5 / rank 16 / 1 epoch | 59.0% | 104.5 px |
| SFT v3 | 1600 条（纯桌面） | **绝对像素** | lr 2e-5 / rank 16 / 1 epoch | **62.7%** | 61.7 px |
| SFT v4 | 606 桌面 + 1200 网页 | 绝对像素 | 同上 | 59.4% | 74.7 px |

¹ v1 只在 61 条分层抽样上测过（当时已明显崩坏，没跑全量）。

v2 相对 v1 是巨大改善（9.8% → 59.0%），但**仍比基座低 21 个点**。
关键在于它并不是"不会定位"，而是**定位变糙了**：偏移 p50 从 24.4 px 退化到 104.5 px。

### 2.4 一个被证伪的假设：训练/推理分辨率不一致

v2 训练时图像被压到 160 万像素（`image_max_pixels`），评测却是全分辨率。
结合第 3 节刚测出的"压分辨率掉 60 个点"，很自然会怀疑是分辨率不一致所致。

**做了对照实验，假设不成立** —— 把 v2 放到它训练时的分辨率下评测：

| 档位 | 原分辨率 | 1.6M px 口径 |
|---|---:|---:|
| 基座 | 80.0% | 20.3% |
| SFT v2 | **59.0%** | 15.7% |

v2 在自己训练时的分辨率下反而更差（15.7% < 59.0%），且两个分辨率下都低于基座。

### 2.5 当前假设：强加 [0,1000] 目标在扰动输出尺度

dump v2 的原始输出可以看到，尽管训练目标写的是 [0,1000]，
模型最终输出的仍然是**绝对像素**：

```
[web 2560x1440] GTcenter=(2425,164)   OUT: {"point": [2389, 164]}   pixel=HIT
[web 2560x1440] GTcenter=(2456,48)    OUT: {"point": [2438, 50]}    pixel=HIT
[desktop 960x540] GTcenter=(932,95)   OUT: {"point": [923, 87]}     pixel=HIT
```

也就是说：**[0,1000] 这个约定没被真正采纳，却把基座原生的像素输出扰动糙了。**

于是第三轮改用 `--target-space pixel`，以基座原生的绝对像素为训练目标，
让微调"顺着基座来"而不是"给基座改规矩"。这是 v3 唯一改动的自变量。

**结果：假设成立，但仍不足以追平基座。**

| 版本 | 准确率 | 偏移 p50 | 相对 v2 |
|---|---:|---:|---|
| SFT v2（[0,1000] 目标） | 59.0% | 104.5 px | — |
| SFT v3（像素目标） | **62.7%** | **61.7 px** | +3.7 点，精度翻倍 |

按平台看 v3 全面优于 v2（mobile 72.5 / web 58.9 / desktop 52.7），
但仍全部低于基座（85.1 / 76.1 / 77.3）。

### 2.5.1 剩下的 17 个点差在哪：数据多样性

三轮下来，能调的都调了（数据量 303→1600、lr 5 倍、rank 减半、1 epoch、
训练目标改成基座原生口径），最好的一版仍比零样本低 17 个点。

再看一眼数据本身，答案就在这：

```
ShowUI-desktop-8K = 7496 个元素 / 101 张桌面截图（每张约 74 个元素）
评测 ScreenSpot  = mobile 502 / web 436 / desktop 334（手机、网页、桌面三类）
```

**训练图只有 101 张、且全是桌面**，而评测里 mobile+web 占 74%。
这不是"数据不够多"，而是"数据不够杂"——LoRA 在 101 张图上反复学，
学到的是这 101 张图的布局，对手机和网页属于分布外。

所以下一步该动的是**数据多样性**（引入 ShowUI-web / mobile），
而不是继续调学习率或训练目标。这是一个靠数据规模解决不了的问题：
1600 条样本听起来不少，但底图只有 101 张。

### 2.7 v4：用"部分下载"拿到网页数据

训练只有 101 张桌面截图，而评测里 mobile+web 占 74%，这是剩余 17 个点的主因。
补数据的难点在于：**ShowUI-web 的图打包在一个 43GB 的 `images.tar.gz` 里**，
全量下载既不划算也不必要。

绕过的办法是利用 HTTP Range 只取前面一段再解压（tar 是顺序存储，
截断的文件照样能解出其中完整的成员）：

```bash
curl -sL -r 0-1610612736 -o web_part.tar.gz \
  "https://hf-mirror.com/datasets/showlab/ShowUI-web/resolve/main/images.tar.gz"
tar -xzf web_part.tar.gz        # 末尾会报错，但完整成员都已解出
```

实测：1.5 GB / 65 秒（约 23 MB/s），解出 **1375 张网页截图**。
标注另外单独下 `metadata/hf_train.json`（113 MB，21988 条），
用 `--web-root` 指过去即可，`01_prepare_data.py` 会自动按 `images/` 之后
的相对路径把标注和图对上（ShowUI-web 的 `img_url` 是制作者机器上的绝对路径）。

> 用过但放弃的数据源：
> - **OS-Atlas-data**：816 GB，全是 46GB 的 zip 分片
> - **GUI-Odyssey**：手机数据，但每个 step 只有"整段任务"的描述，
>   没有"点哪个元素"的指令，指令→坐标的对应太糙，不适合 grounding 训练
> - **ShowUI-web 全量**：43 GB，没必要

**v4 结果：加网页数据没有带来整体提升，甚至略降（62.7% → 59.4%）。**

| 平台 | 基座 | v3（纯桌面） | v4（桌面+网页） | v4 相对 v3 |
|---|---:|---:|---:|---:|
| mobile | 85.1% | 72.5% | **75.5%** | +3.0 |
| web | 76.1% | 58.9% | 48.9% | **−10.0** |
| desktop | 77.3% | 52.7% | 48.8% | −3.9 |
| 总体 | **80.0%** | 62.7% | 59.4% | −3.3 |

数据变杂了，mobile 确实涨了 3 个点，但 web 掉了 10 个点 —— **加的是网页数据，
web 反而变差**，说明不是"补多样性"就能解决。可能的原因：

- ShowUI-web 的截图是 1920×1080 的浏览器页面，而 ScreenSpot 的 web 分档是
  2560×1440，两者在像素尺度上差一档，训练时又被 `image_max_pixels` 压过
- 网页样本挤占了桌面样本（1600 → 606），desktop 也跟着掉了

### 2.8 微调部分的最终结论

四轮下来（数据量、lr/rank、训练目标口径、数据多样性都试过），
**最好的一版是 v3 的 62.7%，仍比零样本基座低 17.3 个点**。

这不是"没调好"，而是一个有解释的结论：

> Qwen2.5-VL-3B 本身已经在大规模 GUI 定位数据上训练过（零样本就能到 80%，
> 与论文锚点 80.9 一致）。在这种基座上，用千级样本的小规模 LoRA
> 既没有新信息可学，又会扰动已经调好的输出尺度 —— 所以是**净损失**。
>
> 要让微调真正有用，需要的是十万级、覆盖各平台的高质量标注，
> 而不是把 101 张桌面截图重复利用。

这个结论同样写进了 README 的结果表：SFT 一栏标注为"负结果"。

> 负面结果照实写进文档，而不是删掉重来：
> "用 4% 的数据微调会把 80% 的定位能力训到 25%" 本身就是可复用的工程结论。

## 3. AWQ W4A16 量化

```
输入    基座 Qwen2.5-VL-3B-Instruct（与零样本基线同一个模型）
方法    llmcompressor 0.5.2 / AWQModifier / W4A16(group_size=128)
校准    32 条真实 GUI 截图（ShowUI-desktop，长边压到 768，非合成图）
产出    3.2 GB（BF16 是 7.1 GB，压到 45%）
内核    Marlin（SM86 上唯一可用）
```

### 3.1 三档实测

| 档位 | 预处理 | 样本 | 准确率 | 保守准确率 | 偏移 p50 |
|---|---|---:|---:|---:|---:|
| BF16 基座 | **原分辨率**（≤12.8M px） | 1257 | **80.0%** | 79.0% | 24.4 |
| BF16 基座 | 上限 1.6M px | 1245 | 20.3% | 19.9% | 357.9 |
| AWQ W4A16 | 上限 1.6M px | 1239 | **16.6%** | 16.2% | 379.0 |

### 3.2 最重要的发现：分辨率比量化重要得多

同一份 BF16 权重，只是把输入图压到 160 万像素，准确率就从 **80.0% 掉到 20.3%
（-59.7 点）**；而在这同一分辨率下，4bit 量化只再损失 **3.7 点**（20.3% → 16.6%）。

按平台看差异的来源非常清楚：

| 平台 | 图像尺寸 | 是否被缩放 | BF16 原分辨率 | BF16 @1.6M | AWQ @1.6M |
|---|---|---:|---:|---:|---:|
| desktop | 多为 960×540 | 否/部分 | 77.3% | 59.0% | 44.7% |
| mobile | 2360×1640 | **是**（×0.6） | 85.1% | 9.7% | 10.6% |
| web | 2560×1440 | **是**（×0.55） | 76.1% | 3.3% | 2.3% |

被缩放的 mobile/web 直接崩到个位数，没被缩放的 desktop 只掉十几点。
dump 原始输出也是同样画面：desktop 上 `(924,87)` 对着 GT `(932,95)` 几乎正中，
而 web 上给出 `(1587,102)` 对着 GT `(2425,164)` —— 差 800 多像素。

> 这条结论直接改写项目的优化优先级：
> **端侧落地时，"保住输入分辨率"的价值远大于"从 16bit 压到 4bit"。**
> 压分辨率的代价是 60 个点，压比特的代价是 4 个点。
> 设计文档里"分辨率是定位任务的命门"这句判断，被这组数字坐实了。

### 3.3 部署这条路上踩的四个坑（详见 `docs/06-error-log.md` 第 5 节）

| 坑 | 表现 | 解法 |
|---|---|---|
| **ignore 命名不匹配** | 视觉塔实际没被量化，vLLM 却报 Marlin 拒绝 3420 维 | llmcompressor 把 ignore 写成 `model.visual.*`，而权重键是 `visual.*`，两种写法都补进 `config.json` |
| bitblas 不可用 | 装了之后启动即 `illegal memory access` | 卸载，回落 Marlin |
| torch.compile 崩 | 栈在 triton 自动调优 | `enforce_eager: true` |
| vLLM profiling 限制分辨率 | dummy 图按 max_pixels 生成，与文本截断长度不一致 → 服务起不来 | 只能把 `max_pixels` 钉在约 1.6M（dummy=2048 token 正好对齐） |

**最后一条是本节最大的遗憾**：受 vLLM 0.8.5 的 dummy-input profiling 限制，
AWQ 档无法在**原分辨率**下服务，所以上面的量化对比只能在 1.6M 像素这个
"双输"工作点上做。要拿到原分辨率下的量化损失，需要换 vLLM 版本
（新版对多模态 dummy 的处理更宽松）—— 这是下一步待办。

## 4. 结论

### 4.1 已坐实的四件事

| # | 结论 | 证据 |
|---|---|---|
| 1 | **评测链路可信** | 零样本 80.0% vs 论文锚点 80.9，差 0.9 个点；失败明细可回溯 |
| 2 | **小目标是短板** | <8k px² 两档 60~63%，>8k 是 86.9%；icon 68.8% vs text 88.9% —— 量化前就存在的 20~27 点落差 |
| 3 | **数据量不足的微调会反向优化** | 303 条（4%）训出 9.8%，零样本是 80.0% |
| 4 | **压分辨率比压比特贵得多** | 同一 BF16 权重：压分辨率 -59.7 点，压到 4bit 只 -3.7 点 |
| 5 | **训练目标应顺着基座原生口径** | 同为 1600 条，[0,1000] 目标 59.0% vs 像素目标 62.7%，偏移 p50 从 104 降到 62 |
| 6 | **微调的瓶颈是数据多样性，不是数据量** | 1600 条样本其实只来自 101 张桌面截图；评测里 mobile+web 占 74%，全是分布外 |

第 3、4、6 条是最反直觉、也最值得写进简历的三条：

- 微调不是"跑了就涨"，数据不合适时它是在**破坏**预训练能力；
- 量化不是端侧部署的主要矛盾，**输入分辨率才是**；
- 样本条数不是瓶颈，**底图多样性才是**（1600 条听起来多，底图只有 101 张）。

### 4.2 尚未完成

| 项 | 状态 | 阻塞点 |
|---|---|---|
| 原分辨率下的量化对比 | 只有 1.6M px 口径的对比 | vLLM 0.8.5 的 dummy profiling 不允许 AWQ 档在原分辨率服务，需换 vLLM 版本 |
| SFT 有效版 | 数据管线已修好（parquet，7496 条） | 需重训（约 1h）+ 重新合并评测 |
| 速度指标（TTFT / 吞吐 / 显存峰值） | 脚本就绪（`vfs.bench`） | 注意两档都必须是 `enforce_eager: true` 才可比 |

### 4.3 下一步（按性价比排序）

1. **用 parquet 的 2000~7500 条重训**（`lr` 2e-5 / `lora_rank` 16 / 1 epoch）
   —— 把 SFT 从负结果翻正，才能回答"微调带来多少提升"
2. **升级 vLLM 到对多模态 dummy 更宽松的版本**，拿到原分辨率下的 BF16 vs AWQ 对比
3. 跑 `vfs.bench` 拿速度与显存峰值，与精度拼成完整选型表

### 4.4 一句话版本

> 在 3090 上用 Qwen2.5-VL-3B 跑通 GUI 定位的评测与量化链路：零样本 80.0%，
> 与论文锚点 80.9 对齐；4bit AWQ 在同等预处理下只损失 3.7 点，而把输入图压到
> 160 万像素会损失 59.7 点 —— 端侧部署的主要矛盾是分辨率，不是比特数。
> 微调做了三轮仍未超过零样本（9.8% → 59.0% → 62.7%），
> 定位出的瓶颈是"101 张底图撑不起 mobile/web 评测"，而非学习率或数据量；
> 另外实测出 AWQ 产物"能生成"与"能部署"是两件事（受 GPU 内核与 ignore 命名影响）。
