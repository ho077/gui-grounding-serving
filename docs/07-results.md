## 2. LoRA 微调：一例失败实验（负面结果）

### 2.1 配置与结果

```
基座    Qwen2.5-VL-3B-Instruct
数据    ShowUI-desktop 303 条（101 张图 × 最多 3 个元素）
LoRA    rank 32 / alpha 64 / target=all，冻结视觉塔，投影层可训
训练    2 epoch、有效 batch 16、lr 1e-4、38 步、19 分钟、loss 0.875→0.66（均值 0.723）
```

训练**机械上完全成功**（adapter 240MB，checkpoint 正常落盘，格式输出 100% 可解析），
但**精度崩了**：

| 模型 | 坐标口径 | 准确率 | 对照 |
|---|---|---:|---|
| 零样本基座 | pixel | **80.0%** | — |
| SFT 后 | norm（[0,1000]） | 9.8% | 61 条分层抽样 |
| SFT 后 | pixel | 24.6% | 同一批样本 |

SFT 确实学会了 `[0,1000]` 归一化输出（训练目标就是这么写的），
但定位精度掉了 3~8 倍，**连它的训练分布 desktop 也只有 25~37%**（零样本 desktop 是 77.3%）。
所以不是"换了个坐标口径导致评测错"，而是模型本身退化了。

### 2.2 第一轮根因（后来被修正）：数据量只用到了 4%

排查顺序（重要：没查清前不要归因给"模型不行"）：

1. 先验数据：坐标是否越界 —— 0 条越界，数据干净
2. 再验预处理：`preprocessor_config.json` 的 `max_pixels` 是否被改成训练时的值 —— 与基座一致
3. 最后查数据规模 —— 脚本只读元数据 JSON，产出 303 条

> **修正（第二轮才看清）**：最初我把"parquet 有 7496 条"理解成"少了 7000 张图"，
> **这个判断是错的**。7496 是**元素数**，ShowUI-desktop-8K 实际只有 **101 张桌面截图**
> （每张约 74 个元素），元数据 JSON 覆盖的也是同样的 101 张，并不"少"。
> 真正的限制是 `max_per_image=3`：101 张 × 3 = 303 条。
>
> 顺带修掉一个隐蔽 bug：`per_img` 原按 `image_url` 去重，而不同 parquet 里存在同名
> `screenshots/message/screen_1.png`，会把不同的图当成同一张（1600 条被压回 303 条），
> 落盘时还会互相覆盖。已改为按**图像内容哈希**去重。

### 2.3 三轮微调的实测

| 版本 | 数据 | 训练目标 | 超参 | 准确率（原分辨率） | 偏移 p50 |
|---|---|---|---|---:|---:|
| 零样本基座 | — | — | — | **80.0%** | 24.4 px |
| SFT v1 | 303 条 | [0,1000] | lr 1e-4 / rank 32 / 2 epoch | 9.8%~24.6%¹ | — |
| SFT v2 | 1600 条 | [0,1000] | lr 2e-5 / rank 16 / 1 epoch | 59.0% | 104.5 px |
| SFT v3 | 1600 条（纯桌面） | **绝对像素** | lr 2e-5 / rank 16 / 1 epoch | **62.7%** | 61.7 px |
| SFT v4 | 606 桌面 + 1200 网页 | 绝对像素 | 同上 | 59.4% | 74.7 px |

¹ v1 只在 61 条分层抽样上测过（当时已明显崩坏，没跑全量）。

v2 相对 v1 是巨大改善（9.8% → 59.0%），但**仍比基座低 21 个点**。
关键在于它并不是"不会定位"，而是**定位变糙了**：偏移 p50 从 24.4 px 退化到 104.5 px。

### 2.4 一个被证伪的假设：训练/推理分辨率不一致

> ⚠️ **本节表格作废（2026-10-19）** —— 右边的"1.6M px 口径"两列是口径污染产物，
> 见 §11.1。基座在同源口径下压到长边 1600 是 **80.5%**（不是 20.3%），
> 所以"SFT v2 在自己训练分辨率下更差（15.7% < 59.0%）"这个推论**不再成立**，
> 需要重跑才算数（目前未重跑）。

v2 训练时图像被压到 160 万像素（`image_max_pixels`），评测却是全分辨率。
结合第 3 节刚测出的"压分辨率掉 60 个点"，很自然会怀疑是分辨率不一致所致。

**做了对照实验，假设不成立** —— 把 v2 放到它训练时的分辨率下评测（该表已作废）：

| 档位 | 原分辨率 | ~~1.6M px 口径~~（作废） |
|---|---:|---:|
| 基座 | 80.0% | ~~20.3%~~ → **80.5%**（见表下注） |
| SFT v2 | **59.0%** | ~~15.7%~~ → 未重跑 |

¹ 修订值与原·2M px 口径不完全等价：这里是客户端长边 1600（服务端 resize 为空操作），
实测 80.5%；旧值是**服务端**降采样 + `auto` 坐标口径。

v2 在自己训练时的分辨率下反而更差（15.7% < 59.0%），且两个分辨率下都低于基座。

### 2.5 当前假设：强加 [0,1000] 目标在扰动输出尺度

dump v2 的原始输出可以看到，尽管训练目标写的是 [0,1000]，
模型最终输出的仍然是**绝对像素**：

```
[web 2560x1440] GTcenter=(2425,164)   OUT: {"point": [2389, 164]}   pixel=HIT
[web 2560x1440] GTcenter=(2456,48)    OUT: {"point": [2438, 50]}    pixel=HIT
[desktop 960x540] GTcenter=(932,95)   OUT: {"point": [923, 87]}     pixel=HIT
```

也就是说：**[0,1000] 这个约定没被真正采纳，却把基座原生的像素输出扰动糙了。**

于是第三轮改用 `--target-space pixel`，以基座原生的绝对像素为训练目标，
让微调"顺着基座来"而不是"给基座改规矩"。这是 v3 唯一改动的自变量。

**结果：假设成立，但仍不足以追平基座。**

| 版本 | 准确率 | 偏移 p50 | 相对 v2 |
|---|---:|---:|---|
| SFT v2（[0,1000] 目标） | 59.0% | 104.5 px | — |
| SFT v3（像素目标） | **62.7%** | **61.7 px** | +3.7 点，精度翻倍 |

按平台看 v3 全面优于 v2（mobile 72.5 / web 58.9 / desktop 52.7），
但仍全部低于基座（85.1 / 76.1 / 77.3）。

### 2.5.1 剩下的 17 个点差在哪：数据多样性

三轮下来，能调的都调了（数据量 303→1600、lr 5 倍、rank 减半、1 epoch、
训练目标改成基座原生口径），最好的一版仍比零样本低 17 个点。

再看一眼数据本身，答案就在这：

```
ShowUI-desktop-8K = 7496 个元素 / 101 张桌面截图（每张约 74 个元素）
评测 ScreenSpot  = mobile 502 / web 436 / desktop 334（手机、网页、桌面三类）
```

**训练图只有 101 张、且全是桌面**，而评测里 mobile+web 占 74%。
这不是"数据不够多"，而是"数据不够杂"——LoRA 在 101 张图上反复学，
学到的是这 101 张图的布局，对手机和网页属于分布外。

所以下一步该动的是**数据多样性**（引入 ShowUI-web / mobile），
而不是继续调学习率或训练目标。这是一个靠数据规模解决不了的问题：
1600 条样本听起来不少，但底图只有 101 张。

### 2.7 v4：用"部分下载"拿到网页数据

训练只有 101 张桌面截图，而评测里 mobile+web 占 74%，这是剩余 17 个点的主因。
补数据的难点在于：**ShowUI-web 的图打包在一个 43GB 的 `images.tar.gz` 里**，
全量下载既不划算也不必要。

绕过的办法是利用 HTTP Range 只取前面一段再解压（tar 是顺序存储，
截断的文件照样能解出其中完整的成员）：

```bash
curl -sL -r 0-1610612736 -o web_part.tar.gz \
  "https://hf-mirror.com/datasets/showlab/ShowUI-web/resolve/main/images.tar.gz"
tar -xzf web_part.tar.gz        # 末尾会报错，但完整成员都已解出
```

实测：1.5 GB / 65 秒（约 23 MB/s），解出 **1375 张网页截图**。
标注另外单独下 `metadata/hf_train.json`（113 MB，21988 条），
用 `--web-root` 指过去即可，`01_prepare_data.py` 会自动按 `images/` 之后
的相对路径把标注和图对上（ShowUI-web 的 `img_url` 是制作者机器上的绝对路径）。

> 用过但放弃的数据源：
> - **OS-Atlas-data**：816 GB，全是 46GB 的 zip 分片
> - **GUI-Odyssey**：手机数据，但每个 step 只有"整段任务"的描述，
>   没有"点哪个元素"的指令，指令→坐标的对应太糙，不适合 grounding 训练
> - **ShowUI-web 全量**：43 GB，没必要

**v4 结果：加网页数据没有带来整体提升，甚至略降（62.7% → 59.4%）。**

| 平台 | 基座 | v3（纯桌面） | v4（桌面+网页） | v4 相对 v3 |
|---|---:|---:|---:|---:|
| mobile | 85.1% | 72.5% | **75.5%** | +3.0 |
| web | 76.1% | 58.9% | 48.9% | **−10.0** |
| desktop | 77.3% | 52.7% | 48.8% | −3.9 |
| 总体 | **80.0%** | 62.7% | 59.4% | −3.3 |

数据变杂了，mobile 确实涨了 3 个点，但 web 掉了 10 个点 —— **加的是网页数据，
web 反而变差**，说明不是"补多样性"就能解决。可能的原因：

- ShowUI-web 的截图是 1920×1080 的浏览器页面，而 ScreenSpot 的 web 分档是
  2560×1440，两者在像素尺度上差一档，训练时又被 `image_max_pixels` 压过
- 网页样本挤占了桌面样本（1600 → 606），desktop 也跟着掉了

### 2.8 微调部分的最终结论

四轮下来（数据量、lr/rank、训练目标口径、数据多样性都试过），
**最好的一版是 v3 的 62.7%，仍比零样本基座低 17.3 个点**。

这不是"没调好"，而是一个有解释的结论：

> Qwen2.5-VL-3B 本身已经在大规模 GUI 定位数据上训练过（零样本就能到 80%，
> 与论文锚点 80.9 一致）。在这种基座上，用千级样本的小规模 LoRA
> 既没有新信息可学，又会扰动已经调好的输出尺度 —— 所以是**净损失**。
>
> 要让微调真正有用，需要的是十万级、覆盖各平台的高质量标注，
> 而不是把 101 张桌面截图重复利用。

这个结论同样写进了 README 的结果表：SFT 一栏标注为"负结果"。

> 负面结果照实写进文档，而不是删掉重来：
> "用 4% 的数据微调会把 80% 的定位能力训到 25%" 本身就是可复用的工程结论。

## 3. AWQ W4A16 量化

```
输入    基座 Qwen2.5-VL-3B-Instruct（与零样本基线同一个模型）
方法    llmcompressor 0.5.2 / AWQModifier / W4A16(group_size=128)
校准    32 条真实 GUI 截图（ShowUI-desktop，长边压到 768，非合成图）
产出    3.2 GB（BF16 是 7.1 GB，压到 45%）
内核    Marlin（SM86 上唯一可用）
```

§3 全文（含 3.1 / 3.2）已于 **2026-10-19 订正**，完整过程与正确数字见 **§11**。
下面保留原文，只加订正标记 —— 删掉会丢掉一次很有价值的排查。

### 3.1 三档实测（旧表，作废）

> ⚠️ 表中两个 1.6M px 数字作废：`bf16_base_cap` 20.3% → **80.5%**，
> `awq_int4` 16.6% → **64.0%**（同源口径、长边 1600）。

| 档位 | 预处理 | 样本 | 准确率 | 保守准确率 | 偏移 p50 |
|---|---|---:|---:|---:|---:|
| BF16 基座 | **原分辨率**（≤12.8M px） | 1257 | **80.0%** | 79.0% | 24.4 |
| ~~BF16 基座 | 上限 1.6M px | 1245 | 20.3% | 19.9% | 357.9~~ |
| ~~AWQ W4A16 | 上限 1.6M px | 1239 | **16.6%** | 16.2% | 379.0~~ |

### 3.2 最重要的发现：分辨率比量化重要得多（**已驳回，见 §11**）

> ⚠️ **本节结论已推翻。** "压分辨率 −59.7 点"是测量口径污染；
> "4bit 只 −3.7 点"同样是污染下的差值。订正后的事实：
> **长边 1024~1280 与原分辨率统计上不可区分**，而 **4bit 要付出 12~16 点** ——
> 优先级正好反过来：先缩图（免费），再决定要不要量化（有价）。

同一份 BF16 权重，只是把输入图压到 160 万像素，准确率就从 **80.0% 掉到 20.3%
（-59.7 点）**；而在这同一分辨率下，4bit 量化只再损失 **3.7 点**（20.3% → 16.6%）。

按平台看差异的来源非常清楚（**这张表反而是最关键的证据，它被证明全部来自链路而非模型**）：

| 平台 | 图像尺寸 | 是否被缩放 | BF16 原分辨率 | BF16 @1.6M | AWQ @1.6M |
|---|---|---:|---:|---:|---:|
| desktop | 多为 960×540 | 否/部分 | 77.3% | 59.0% | 44.7% |
| mobile | 2360×1640 | **是**（×0.6） | 85.1% | 9.7% | 10.6% |
| web | 2560×1440 | **是**（×0.55） | 76.1% | 3.3% | 2.3% |

被缩放的 mobile/web 直接崩到个位数，没被缩放的 desktop 只掉十几点。
dump 原始输出也是同样画面：desktop 上 `(924,87)` 对着 GT `(932,95)` 几乎正中，
而 web 上给出 `(1587,102)` 对着 GT `(2425,164)` —— 差 800 多像素。

> ⚠️ **上面这段推理错在一个地方**：当时把"被缩放 → 崩"读成了模型的分辨率敏感性，
> 实际是：服务端降采样后 **GT 框没有跟着缩**，预测天然偏小 0.55~0.6 倍，
> desktop 幸存只是因为它的图大多没超过 1.6M px。三个不同模型档崩在同一处，
> 恰恰说明它与模型无关。详见 §11.1。

> ~~这条结论直接改写项目的优化优先级：~~
> ~~**端侧落地时，"保住输入分辨率"的价值远大于"从 16bit 压到 4bit"。**~~
> ~~压分辨率的代价是 60 个点，压比特的代价是 4 个点。~~
> **订正后**：保住输入分辨率确实重要，但**重要到什么程度**完全不同 ——
> 缩到长边 1024~1280 是免费的（−0 点，token −3~4.4×），再往下才悬崖；
> 而 4bit 的真实代价是 **12~16 个点**。优先级：**先缩图，再谈量化**。

### 3.3 部署这条路上踩的四个坑（详见 `docs/06-error-log.md` 第 5 节）

| 坑 | 表现 | 解法 |
|---|---|---|
| **ignore 命名不匹配** | 视觉塔实际没被量化，vLLM 却报 Marlin 拒绝 3420 维 | llmcompressor 把 ignore 写成 `model.visual.*`，而权重键是 `visual.*`，两种写法都补进 `config.json` |
| bitblas 不可用 | 装了之后启动即 `illegal memory access` | 卸载，回落 Marlin |
| torch.compile 崩 | 栈在 triton 自动调优 | `enforce_eager: true` |
| vLLM profiling 限制分辨率 | dummy 图按 max_pixels 生成，与文本截断长度不一致 → 服务起不来 | 只能把 `max_pixels` 钉在约 1.6M（dummy=2048 token 正好对齐） |

**最后一条是本节最大的遗憾**：受 vLLM 0.8.5 的 dummy-input profiling 限制，
AWQ 档无法在**原分辨率**下服务，所以上面的量化对比只能在 1.6M 像素这个
"双输"工作点上做。要拿到原分辨率下的量化损失，需要换 vLLM 版本
（新版对多模态 dummy 的处理更宽松）—— 这是下一步待办。

## 5. 速度与显存：量化换不来速度，换得来"能不能塞进去"

> ✅ **本节结论未被订正**，且因为 1408px 恰好落在 §11 的"无损平台区"（长边 1024~1280），
> 这组速度数字反而更有代表性 —— 它描述的正是推荐的工作点，而不是一个被压坏的输入。

压测口径（与真实用法对齐）：**1408px 图（≈评测时的有效分辨率）、max_tokens 32、
并发 8、64 请求、4 预热**，两档均为 `enforce_eager`（AWQ 必须，BF16 对齐同一把尺）。

| 指标 | BF16 | AWQ W4A16 | 差异 |
|---|---:|---:|---:|
| TTFT p50 | 1115 ms | 1129 ms | +1.2% |
| TTFT p95 | 2789 ms | 2828 ms | +1.4% |
| TPOT 均值 | 134.8 ms | 145.3 ms | **+7.8%** |
| 输出吞吐 | 44.83 tok/s | 42.53 tok/s | −5.1% |
| 请求吞吐 | 1.51 req/s | 1.45 req/s | −3.8% |
| 峰值显存（0.9 预算） | 21.59 GiB | 21.60 GiB | 持平 |
| **0.45 预算（10.8GB）** | ❌ 启动失败 | ✅ 正常服务，实测 **8.7 GiB** | — |

### 5.1 4bit 在 3090 上没有速度收益，反而略慢

TPOT 和吞吐都小幅劣化。原因有两个：

1. **W4A16 是 weight-only 量化**：解码每一步都要把 4bit 权重解包回 16bit 再参与
   矩阵乘，解包开销吃掉了一部分带宽收益 —— 这是 4bit 在小 batch、显存-bandwidth
   受限场景下的通病，batch 越大才越能摊薄
2. **AWQ 档位必须 `enforce_eager`**（见第 3.3 节，torch.compile 在量化模型上会崩），
   关掉 CUDA Graph 又添了一层固定开销

> 所以"量化=更快"是错的。在单卡 3090、batch 8、输出 32 token 的 GUI 定位场景下，
> **4bit 换来的是显存，不是速度。**

### 5.2 并发扫描：加大 batch 也没有让 4bit 反超

既然"batch 越大越能摊薄解包开销"，就把并发从 8 扫到 32 验证：

| 并发 | 档位 | 完成/失败 | TTFT p50 | TPOT 均值 | 输出吞吐 |
|---|---|---:|---:|---:|---:|
| 8 | BF16 | 64 / 0 | 1115 ms | 134.8 ms | 44.83 tok/s |
| 8 | AWQ | 64 / 0 | 1129 ms | 145.3 ms | 42.53 tok/s |
| 16 | BF16 | 96 / 0 | 1605 ms | 235.6 ms | 52.35 tok/s |
| 16 | AWQ | 96 / 0 | 2052 ms | 242.6 ms | 50.66 tok/s |
| 32 | BF16 | 128 / 0 | 6994 ms | 340.3 ms | 53.72 tok/s |
| 32 | AWQ | 128 / 0 | 7248 ms | 352.8 ms | 51.22 tok/s |

**三个并发档位下 AWQ 都没有反超**（吞吐差距 −5.1% → −3.2% → −4.7%），
且在 c16 之后吞吐就饱和在 53 tok/s 左右不再增长。

这说明该场景的瓶颈**不是显存带宽，而是算力**：

- 1408px 图 ≈ 2048 个图像 token，prefill 算力吃满
- 3B 模型 + 32 token 输出，decode 阶段算力也没闲着
- 4bit 权重省的是**显存带宽**，而我们缺的是**算力**，所以省不到点子上

> 附带一个部署侧观察：并发从 8 加到 32，TTFT p50 从 1.1 秒涨到 7 秒（6 倍），
> 而吞吐只涨 20%。**对 GUI 定位这种交互式场景，盲目加并发是在拿首字延迟换总吞吐**，
> 并不划算 —— 用户等的是第一次坐标，不是队列消化速度。

### 5.2 真正的收益：能不能塞进显存

同样 10.8GB 预算（`gpu_memory_utilization=0.45`）下：

| 档位 | 结果 |
|---|---|
| BF16（权重 7.1GB） | ❌ `ValueError: No available memory for the cache blocks` |
| AWQ W4A16（权重 3.2GB） | ✅ 正常起服务，实测占用 **8.7 GiB** |

权重从 7.1GB 降到 3.2GB（−55%），省下的 3.9GB 在 24GB 卡上不痛不痒，
但在**显存更紧的场景**（同卡跑第二个模型、更长上下文、更高并发）就是能不能部署的区别。

> 部署选型的三条结论，按重要性排序：
> 1. **先保住输入分辨率**（−59.7 点 vs 量化的 −3.7 点）
> 2. **再确认推理引擎在目标 GPU 上有对应内核**（否则产物根本起不来）
> 3. **最后才考虑压比特** —— 它省显存，不省时间

### 5.3 压测前必须做的一次校验

这一轮压测第一版是废的：**64 个请求失败了 39 个**，而服务端零报错。
根因是两个 vLLM 服务同时监听 8000 端口（SO_REUSEPORT），请求被分流，
一半打到旧服务上，返回 `404 The model ... does not exist`。

污染范围：AWQ 压测全部作废；AWQ 精度评测也有少量请求受影响
（修正后准确率 16.6% → 16.8%，结论不变）。

**压测前的固定动作**：

```bash
ps aux | grep -c '[a]pi_server'      # 必须是 1
```

结果里的 `failed_requests` 必须是 0，否则这组数字不能用来对比。

这也是本项目坚持"所有档位同口径对比"的原因。

### 7.3 量化：找到了最接近的先例，且结论互相印证

此前检索"GUI 模型量化"几乎空白，这次找到两类高度相关的工作：

**Mano-P（2026，端侧 GUI-VLA）**：4B 模型用 **W4A16** 量化跑在 Apple M4 Pro 上，
峰值内存 4.3GB、prefill 476 tok/s、decode 76 tok/s，OSWorld 58.2%（当时第一）。
它的定位和我们完全一致——"端侧跑 GUI Agent"，且同样选了 W4A16。

**Cider SDK 的量化对比（2026）**：
- MLX 原生只支持 W4A16，"内存带宽瓶颈在激活读取上"
- 它实现 W8A8 在线激活量化，**M5 Pro 上 per-channel W8A8 比 MLX W4A16 的
  prefill 快 1.4~2.2 倍**
- 代价：CUA Benchmark 准确率 58% → 54%，**掉 4 个点**换 prefill ≈1453 tok/s

这和我们的两条结论几乎逐条对应：

| 我们的实测（**订正后**） | Cider 的实测 |
|---|---|
| **W4A16 掉 12~16 点**（80.5%→64.0%，同口径） | W8A8 掉 4 点（58% → 54%） |
| **4bit 不省时间，TPOT 反而 +7.8%** | W4A16 的瓶颈在**激活读取**，不是权重 |
| 瓶颈是算力（prefill 吃满），非显存带宽 | 提速靠**激活量化**（W8A8），不是权重量化 |
| 省下的显存换来"塞得进"（8.7 vs 10.8GB） | 4.3GB 峰值内存才能上端侧 |

两条独立证据链指向同一件事：**W4A16 省的是权重带宽，而 GUI grounding 的瓶颈在
prefill 算力与激活读取**。要真提速，方向是激活量化（W8A8）或视觉 token 剪枝
（Mano-P 的 GS-Pruning 保留约 25% token，吞吐 ×3），而不是继续压权重比特。

> 订正后第一行**不再与 Cider 接近，而是明显更贵**（12~16 点 vs 4 点）。这不是矛盾，
> 是可解释的差异：Cider 量的是 **W8A8**（权重仍留 8bit），我们压到 **W4A16**；
> 且我们的基座只有 3B、评测是 ScreenSpot 的逐点命中。**结论方向因此更强而非更弱**：
> 把权重压到 4bit 的代价显著高于压到 8bit，支持"Cider 路线走得通，别往 4bit 卷"。

> 这条对比把我们的结论从"在 3090 上观察到的一个现象"升级成了"有独立证据支撑的判断"，
> 也直接给出了下一步该试什么（W8A8 / token 剪枝），而不是继续在 W4A16 上调参。

### 7.4 分辨率：多篇 2025-2026 论文独立支持"分辨率重要"（**具体trade-off 已订正**）

> ⚠️ 下面的引子"我们最核心的发现是 −59.7 vs −3.5"已作废，订正后的数字见 §11：
> **长边 1024~1280 无损、768 −8.5、512 −35.2**。
> 与文献的**方向**仍然一致（分辨率确实是命门），但**拐点位置**是本项目的新信息。

~~我们最核心的发现是"压分辨率 −59.7 点 vs 压比特 −3.5 点"。~~ 检索到的先例：

- **SE-GUI（NeurIPS 2025）** 专门做了分辨率消融："max_pixels 从 1M 到 5M，
  随分辨率提升，模型识别小而关键的 UI 元素的能力持续改善"—— 和我们的方向一致
- **AutoFocus（2026）** 明确称之为 **resolution-bottleneck hypothesis**，
  并指出免训练主动搜索在 ScreenSpot-Pro（高分辨率专业软件）上增益最大（+8.6~17.5 点），
  在已接近饱和的 ScreenSpot-v2 上增益小
- **DRS-GUI（2026）** 结论："perceptual scope control, not parameter count,
  is a primary bottleneck"；Qwen2.5-VL-3B + 区域搜索（28.7%）甚至超过 OS-Atlas-7B（18.9%）

**我们的增量（订正后重写）**：这些工作证明了"分辨率/感知范围重要"，
但**没有人把它的代价和压比特的代价放在同一把尺上量过**。我们给出的是一个可部署决策，
而且订正后的版本对工程更友好：

> **不是"不惜代价保分辨率"，而是"存在一个免费缩图区间"** —— 长边 1024~1280
> 精度与原分辨率统计上不可区分、视觉 token 少 3~4.4 倍；真正的精度成本是量化（12~16 点）。
> 两条成本曲线**不在同一个数量级上**：一条有平台区，另一条是陡坡。

### 7.5 微调负结果：被一篇论文的数据完美印证

我们四轮微调最好 62.7%，比零样本低 17.3 点。GUI-Actor 的表 3（LiteTrain 设定，
**只训新增的 action head ≈100M 参数、冻结 VLM 主干**）给出了极具可比性的数字：

| 模型 | ScreenSpot-v2 |
|---|---:|
| Qwen2.5-VL-3B 零样本 | 80.9 |
| GUI-Actor-3B-LiteTrain（Hit@1） | **81.4** |
| GUI-Actor-3B-LiteTrain（Hit@3） | 90.5 |
| GUI-Actor-3B 全量训练（3M+ 样本） | 91.0 |

**即使用了一个专门设计的 action head、冻结主干这个最保守的设定，3B 基座上的
小规模微调也只换来 +0.5 点。** 这和我们的结论一致：在这个已经很强的基座上，
小规模微调没有新信息可学；要涨到 91 需要的是百万级数据（GUI-Actor 全量 3M+）。

我们比它多走一步：定位出了**瓶颈是底图多样性**（1600 条样本只来自 101 张截图），
而不是学习率或训练目标格式。

## 9. 冲击 SOTA 的尝试：为什么"零成本提精度"走不通

目标：**在不增加推理成本的前提下把精度从 80.0% 往上推**。这条线做了 5 组对照实验，
结论全部为负 —— 但每一组都排除了一个方向，且都有数字。

### 9.1 免费杠杆早已用尽

文献里所有增益只来自两个方向：**训练数据**（Jedi 400 万样本、GUI-Actor 300 万+）
或**测试时计算**（GTA1 的 N=8、AutoFocus 的多次搜索）。唯一"免费"的杠杆是输入分辨率，
而我们在第 1 节已经把它开到满（12.8M px）—— 那就是 80.0%。

### 9.2 五组对照实验（同一批 60~90 条样本，同服务、同 prompt）

| # | 尝试 | 结果 | 结论 |
|---|---|---|---|
| 1 | 两阶段「粗定位 → 裁剪放大 → 精定位」 | 78.3% → **73.3%**（−5.0），延迟 +21% | 粗定位自己只有 78%，裁剪框瞄不准；且精修会**改坏已经正确的预测** |
| 2 | oracle 裁剪（裁剪框完美对准真值） | 78.3% → **55.0%**（−23.3） | **裁剪破坏界面上下文**，模型认不出元素了 |
| 3 | 全局平移校正（利用输出偏差） | 80.9% → **68.5%**（−12.4） | 那 +28.7px 的"偏差"主要来自 bbox 几何不对称，不是可校正的系统误差 |
| 4 | 更高并发 / 更大 batch（第 5.2 节） | 三档并发 4bit 均未反超 | 瓶颈在算力，不在带宽 |
| 5 | ~~压分辨率换速度（第 3 节） | 20.3%（−59.7） | 分辨率是精度命门，不能动~~ | **已订正**：压到长边 1024 是 −0.1 点（token −4.4×），见 §11 |

第 2 条是最有意思的：它和 GUI-Eyes / AutoFocus / DRS-GUI 的结论**方向相反**。
那些方法确实靠裁剪涨点，但它们是**专门训练过**才会用裁剪的（GUI-Eyes 用 RL 学
"何时裁、裁多大"）。未经训练直接裁，在这个模型上是净损失。

> 这条负面结论本身有价值：它说明「把 SOTA 的推理期技巧直接搬到强基座上」
> 不成立，必须先验证基座是否吃这一套。我们用 5 组实验把这条路堵死了，
> 省下的是后续开发者几周时间。

### 9.3 真正能涨点的路：换权重（已部分验证）

文献里唯一符合"不增加推理复杂度"的涨点方式是**用一个更好的 checkpoint**：

| 模型 | ScreenSpot（论文） | 相对我们 | 架构 | 集成难度 |
|---|---:|---:|---|---|
| Qwen2.5-VL-3B（我们的零样本） | 80.0 | — | — | — |
| **Jedi-3B**（NeurIPS'25 spotlight） | **88.6** | **+8.6** | 标准 Qwen2.5-VL 微调 | **低**，可直接插现有框架 |
| GUI-Actor-3B | 91.0 | +11.0 | 需自定义 action head | 高，要改模型代码 |

#### 已完成的验证（2026-10-19）：协议对了才能谈精度

| 阶段 | 结果 | 卡在哪 |
|---|---|---|
| ❌ 用主评测的 `{"point":[x,y]}` prompt | 11.0% → 弃用 | 不仅协议错，`--max-side` 缩图后 **GT 没跟着缩**（`docs/06-error-log.md` 第 31 条） |
| ✅ 复刻官方 **ComputerUse 工具调用**协议（`src/vfs/jedi_eval.py`） | **82.0%**（1270 条） | 输入上限只能到 ≤1.8M px（第 33 条） |

**Jedi-3B 全量实测**：**82.0%**，比基座 **+2.0 点**，偏移 p50 从 24.4 px 降到 **8.6 px**。
分平台 desktop 80.2 / mobile 81.6 / web 83.9；icon 74.4 / text 88.4。
定位**更稳**（p50 只有基座的 1/3），不只是分高 —— 这对下游 GUI agent 比准确率差 2 点更有意义。

**为什么没到论文的 88.6**：

1. **输入上限**：论文口径 1080p 以上，而本机该 checkpoint 在 vLLM 0.8.5 下输入
   ≥约 1.9M px 会**永不调度**（不报错），只能跑 ≤1.8M px 口径。
2. **协议细节**：这个模型吃的是工具调用格式，任何出入都会掉点；我们已经逐字段对齐，
   但论文评测脚本未完全开源，无法保证逐字节一致（这也是"论文数字依赖协议"的又一个例证）。

下一步：换更高版本的 vLLM（新版对多模态 dummy 更宽松）拿全分辨率，或用 transformers
直接推理绕开引擎限制。

> 简历上可写的数字（**已实测，见上**）：
> 「更换 NeurIPS'25 的 Jedi-3B 权重，ScreenSpot 从 80.0% → **82.0%**（+2.0），
> 坐标偏移 p50 从 24.4px 降到 **8.6px**（−64%）；同架构、单次 forward，推理成本不变」。
> 别写 88.6 —— 那是我们没能复现的**论文**数字。

### 10.1 已坐实的十一件事

| # | 结论 | 证据 |
|---|---|---|
| 1 | **评测链路可信** | 零样本 80.0% vs 论文锚点 80.9，差 0.9 个点；失败明细可回溯 |
| 2 | **小目标是短板** | <8k px² 两档 60~63%，>8k 是 86.9%；icon 68.8% vs text 88.9% —— 量化前就存在的 20~27 点落差 |
| 3 | **数据量不足的微调会反向优化** | 303 条（4%）训出 9.8%，零样本是 80.0% |
| 4 | ~~**压分辨率比压比特贵得多**~~ → **订正：缩图有免费平台区，量化才是贵的一方** | 同一份 400 条子集：长边 1024~1280 与原分辨率统计上不可区分（81.3 / 82.9 / 81.4，1σ≈2 点），token −3~4.4×；而同口径 4bit 要 −12~−16 点（80.5% → 64.0%）。旧值 −59.7 是口径污染 |
| 5 | **训练目标应顺着基座原生口径** | 同为 1600 条，[0,1000] 目标 59.0% vs 像素目标 62.7%，偏移 p50 从 104 降到 62 |
| 6 | **微调的瓶颈是数据多样性，不是数据量** | 1600 条样本其实只来自 101 张桌面截图；评测里 mobile+web 占 74%，全是分布外 |
| 7 | **4bit 量化换显存，不换速度** | TPOT 反而 +7.8%；但 10.8GB 预算下 BF16 起不来、AWQ 只占 8.7 GiB。**代价（订正后）是 12~16 个点**，偏移 p50 从 17.4 涨到 62.8px（×3.6） |
| 8 | **GUI grounding 的论文数字高度依赖评测协议** | 同一模型（Qwen2.5-VL-3B）在 ScreenSpot-v2 上有 39.1 / 46.9 / 80.9 三种公开值；我们实测 80.0 与 GUI-Actor 的 80.9 对齐。Jedi 88.6 vs 我们实测 82.0 是同类的另一例 |
| 9 | **"零成本提精度"在此场景不成立** | 5 组对照实验全负：两阶段缩放 −5.0、oracle 裁剪 −23.3、平移校正 −12.4、并发扫描无反超。~~压分辨率 −59.7~~ 该项已作废（见 §11） |
| 10 | **换权重比调技巧有效** | Jedi-3B 官方协议 82.0%（+2.0），偏移 p50 24.4 → 8.6 px；同架构单次 forward，推理成本不变 |
| 11 | **测量自己的链路比测模型更难** | 两个旗舰数字先后被自己推翻（−59.7 / −3.5），根因是"缩放、GT、坐标口径"三者不同源 |

第 3、4、6、7、8、10、11 条是最反直觉、也最值得写进简历的条目：

- 微调不是"跑了就涨"，数据不合适时它是在**破坏**预训练能力；
- **先缩图再谈量化**：缩到长边 1024~1280 免费（token −3~4.4×），4bit 才要付 12~16 点；
- 样本条数不是瓶颈，**底图多样性才是**（1600 条听起来多，底图只有 101 张）；
- **4bit 不会让推理变快**，在 3090 + batch 8 的场景下 TPOT 反而涨 7.8%，
  它的价值是把"塞不进显存"变成"塞得进"；
- **跨论文的 GUI 定位数字不可直接比**，同一个模型能差出 40 个点，
  同一个好模型（Jedi）论文 88.6 我们只测到 82.0；
- **SOTA 的推理期技巧不能直接搬到强基座上**：裁剪放大在未训练过的模型上是净损失
  （oracle 裁剪 −23.3），必须先验证基座是否吃这一套；
- **数字差一个数量级时先怀疑自己的测量**（第 11 条）：这次两个"旗舰结论"被自己的
  口径污染推翻，是全场最有教学价值的一课。

### 11.1 过程：一个被三个档位互相"印证"的错误

**起因**。为了测 Jedi-3B，给评测脚本加了 `--max-side`（客户端缩图）。
跑出来的 Jedi 只有 **11.0%**，而且形态很怪：desktop 38.3%、mobile 1.0%、web 1.6%。
当时先排了协议问题（第 32 条），顺着这条线一路查到 `--max-side` 的 GT 没跟着缩（第 31 条）。

**顺手做的一次复核**。既然"缩图会出错"，就去复核早先那组"压分辨率"的结论。
那时它是项目最结实的一个发现：

| 档位（旧） | 准确率 | desktop | mobile | web | 偏移 p50 |
|---|---:|---:|---:|---:|---:|
| BF16 基座 @1.6M px | 20.3% | 59.0% | 9.7% | 2.3% | 357.9 |
| AWQ W4A16 @1.6M px | 16.6% | 44.7% | 10.6% | 2.8% | 379.0 |
| SFT v2 @1.6M px | 15.7% | 41.0% | 10.4% | 2.5% | 406.1 |

三个**不同**的模型档（未微调 / 量化 / 微调），崩在同一个地方、同一个形态。
当时把这件事读成"结论很稳健"。现在看，这恰恰是**最强的反向证据**：
模型不一样，错法却一模一样 —— 错的只能是公共的那段链路。

**对照组的关键一步**：把"谁会被缩放"这件事单独拎出来。翻数据集：

| 平台 | 图像 >1.6M px 的比例 | p50 像素数 | 最大像素数 |
|---|---:|---:|---:|
| desktop (334) | **35%** | 1.12M | 5.94M |
| mobile (502) | **100%** | 2.96M | 3.87M |
| web (436) | **100%** | 3.69M | 3.69M |

**结论就写在这张表里**：desktop 有三分之二根本没超过 cap，所以它"幸存"；
mobile/web 全部被降采样，所以它们"崩"。所谓"平台差异"，其实 = "有没有被降采样"。

**根因**（三件事必须同源，当时三个都不在一条链上）：

1. 图在**服务端**被 `--mm-processor-kwargs max_pixels` 降采样，而 GT 框还在原图坐标系里 ——
   预测天然被系统性缩小 0.55~0.6 倍；
2. 该批评测用的是 `--coord-space auto`，把绝对像素误判成 [0,1000] 归一化后又乘了一次分辨率；
3. 两者叠加，且正好只作用于超限的图。

### 11.2 订正后的做法：三同源

现在的规矩写死在 `scripts/06_ladder.sh` 里：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 缩放位置 | **只在客户端**（`--max-side`），服务端 `max_pixels` 足够大使 resize 为空操作 | 缩放发生在评测脚本可见的一侧，GT 才能跟着缩 |
| GT | `_xywh_to_xyxy` 用**原始**分辨率判定 xywh/xyxy/归一化，再乘缩放系数；并自检"缩前后相对坐标偏差必须为 0" | 用缩放后的尺寸判定会导致 `x+w` 越过边界 → 被误判成 xyxy → 整份标注作废 |
| 坐标口径 | 显式 `--coord-space pixel` | `auto` 会把 923 这类值读成归一化 |

加了自检后，1272 条样本的框全部落在图像界内、缩放前后相对坐标最大偏差 0.0000。

### 11.6 这次学到的一条方法

> **内部自洽不等于对。** 一个错误能在 BF16 / AWQ / SFT 三个档位上稳定复现，
> 说明它 reproducible，不说明它 valid。
>
> 便宜的外部锚点不难找，本项目事后总结的三条：
> 1. **看差异能不能被一条与模型无关的事实解释掉**（这里是"谁被降采样了"）；
> 2. **跨方式为保：**同一样本的预测坐标应当与 GT 在同一坐标系，用"是否落在图像界内"
>    这种几何自检，比看准确率敏感得多（GT 越界时准确率会静默崩塌）；
> 3. **同一条件重复两遍**可以用来估噪声（这里 ≈±2 点），小于噪声的差异不许写进结论。

## 12. 4bit 的 12 点损失，到底在哪个模块上（混合位宽归因）

第 11 节把"压分辨率"的账算清之后，剩下最大的未解问题是：
**同样 12 个点的 4bit 损失，是视觉塔、跨模态投影、还是 LLM 主干造成的？**
如果能把损失定位到具体模块，就能给出"保哪些层"的部署建议 —— 这是算法岗意义上
自己的方法贡献，而不是"我跑了一个量化"。

### 12.1 先排除两个嫌疑人

| 嫌疑人 | 是否被量化 | 结论 |
|---|---|---|
| 视觉塔（667M 参） | **从未被量化** | 现有 AWQ 产物的 `ignore` 里 162 条全是 `visual.*`；且视觉塔中间维 3420，不满足 Marlin 内核 `out_features % 64 == 0`，**在这条路上根本没有被量化的资格** ⇒ 排除 |
| `lm_head`（311M 参） | 从未被量化 | 同上，且它直接决定输出的坐标词元，风险收益比最差 ⇒ 排除 |
| LLM 主干（2775M 参：attn 340M + mlp 2435M） | **全部压成 int4** | ⇒ **−12 点 100% 来自这里** |

也就是说，实验还没开始，损失的可疑范围已经被压缩到 2775M 参数里。剩下的问题是
这 2775M 内部的分布。

### 12.2 2×2 归因矩阵（attention × MLP）

全部在同一口径下取得：**客户端长边 1264 + GT 同比缩放 + `--coord-space pixel`**，
ScreenSpot 全量 1272 条（拒答不计入 n），同一份 BF16 校准集、同一套 `W4A16`
（group 128 / symmetric）量化超参（量化后逐字段比对过产物 config）。

|  | MLP int4 | MLP FP16 |
|---|---:|---:|
| **attention int4** | **67.7%**（V0，3.2 GB） | **78.7%**（keep_mlp，6.5 GB） |
| **attention FP16** | 70.0%（keep_attn，3.7 GB） | **79.7%**（BF16，7.1 GB） |

| 档位 | 权重体积 | 准确率 | 相对 BF16 | 偏移 p50 | 解析失败/拒答 |
|---|---:|---:|---:|---:|---:|
| BF16 基座 | 7.1 GB | 79.7% | — | 16.3 px | 0 / 29 |
| V0：全 int4 | 3.2 GB | 67.7% | **−11.9**（p<0.001） | 44.3 px | 12 / 24 |
| keep_attn | 3.7 GB | 70.0% | −9.7 | 35.5 px | 8 / 26 |
| keep_deep（24–35 层全保） | 4.5 GB | 67.4% | −12.3 | 46.1 px | 29 / 47 |
| keep_mlp | 6.5 GB | 78.7% | **−0.9**（p<0.001） | 17.3 px | 0 / 45 |

**四个格子读出来的结论**：

1. **MLP 是损失的主承载者。** 只把 MLP 保回 FP16（attention 仍 int4），
   准确率从 67.7% 回到 78.7%，**拿回了 11.0 / 11.9 个点**（p<0.001）。
   偏移 p50 同步从 44.3 px 回到 17.3 px（BF16 是 16.3 px）。
2. **attention 几乎不承载损失。** 只保 attention（+0.5 GB）只换回 2.2 个点，
   两比例 z 检验 p=0.23，**不显著**。
3. **"保深层"完全无效。** 把 24–35 层的全部 Linear 保 FP16（+1.4 GB），
   相对 V0 是 −0.3 点（p=0.86）。这条排除了一类常见直觉：
   "深层负责语义/决策，所以更敏感"在坐标回归上不成立。
4. **量化的副作用最先出现在输出格式上。** V0 有 12 条解析失败，keep_mlp 是 0 条
   （与 BF16 持平）；keep_deep 反而涨到 29 条。4bit 不只是"坐标偏一点"，
   它会让模型连 `{"point": [x, y]}` 这种格式都开始写错。

### 12.3 把结论换算成部署语言

| 想挽回的精度 | 付出的显存 | 换来 |
|---|---:|---|
| 保 attention FP16 | +0.5 GB | +2.2 点（不显著，p=0.23） |
| 保 MLP FP16 | +3.4 GB | +11.0 点（显著，p<0.001） |
| 保 24–35 深层 FP16 | +1.4 GB | 0 点 |

⇒ **"该保谁"不是均匀切蛋糕，而是有明确的归因**：4bit 的损失按参数量落在 MLP 上。
这也解释了为什么"混合位宽"在文献里少有公开可用的配方 —— 敏感度分布和
数据/任务强相关，必须逐任务实测，不能照搬 LLM perplexity 实验的结论
（那些实验通常报告 MLP 更耐压，而这里恰好相反）。

### 12.4 MLP 内部再拆一刀：位置比参数量重要

`keep_mlp` 已说明 11 个点在 MLP，但 MLP 有两块参数量差 3 倍的投影：
`gate_up_proj`（1824M，SwiGLU 的门控/扩张）与 `down_proj`（611M，写回残差流）。
保 FP16 的代价分别是 +2.55 GB 与 +0.85 GB。实测（同口径全量 1272）：

| 档位 | 权重体积 | 准确率 | 相对 BF16 | 相对 V0 | p（vs V0） | 偏移 p50 | 解析失败 |
|---|---:|---:|---:|---:|---:|---:|---:|
| BF16 基座 | 7.1 GB | 79.7% | — | +12.0 | <0.001 | 16.3 px | 0 |
| V0：全 int4 | 3.2 GB | 67.7% | −11.9 | — | — | 44.3 px | 12 |
| keep_mlp_gateup（gate/up 保 FP16） | 5.7 GB | **76.4%** | −3.2 | **+8.7** | **<0.001** | 19.9 px | 0 |
| keep_mlp（MLP 全保） | 6.5 GB | 78.7% | −0.9 | +11.0 | <0.001 | 17.3 px | 0 |
| keep_mlp_down（down 保 FP16） | 4.3 GB | **64.0%** | **−15.6** | **−3.7** | 0.057 | 57.4 px | **70** |

三条读数：

1. **门控（gate/up）承载几乎全部的损失**：只保 gate_up（+2.55 GB）就拿回 8.7 点，
   已经覆盖 keep_mlp 全部收益（11.0 点）的 79%；剩下的 2.3 点由 down_proj 贡献。
2. **保 down_proj 不但没用，反而更差**（67.7% → 64.0%，解析失败 12 → 70 条）。
   这不是加载假象：keep_mlp_down 与 V0 的 `gate_proj/up_proj` 量化 scale
   **逐位相同**（已验证到小数点后 10 位），两者唯一的差别就是 down_proj 的精度。
   一个说得通的机制：down_proj 也被量化时，它顺带把 gate/up 注入的高频误差
   低通滤掉一部分；把它换成精确值，噪声反而全额写回残差流。
   **这条是"混合位宽不能按参数量分配"最直接的反例** —— 按参数量看，
   down_proj 只占 MLP 的 25%，保它似乎很划算；实测是负收益。
3. **量化损伤最先伤输出格式**：keep_mlp_down 的 70 条解析失败里，模型开始写出
   `{"point": [.5, .5}`、`{"point_2d": [, y]}`、`{"point_2d": [[305,1084]], "label": ...}`
   这类既不符合我们的 prompt、也不完整的 JSON。4bit 不只是"坐标偏几个像素"，
   它会让模型的输出分布先崩。

### 12.5 七档汇总：精度-显存 Pareto

| 档位 | 权重体积 | 准确率 | 相对 BF16 | 偏移 p50 |
|---|---:|---:|---:|---:|
| BF16 基座 | 7.1 GB | 12.0 GiB | 79.7% | — | 16.3 px |
| keep_mlp（MLP 全保 FP16） | 6.5 GB | 9.6 GiB | 78.7% | −0.9 | 17.3 px |
| keep_mlp_gateup | 5.7 GB | 8.4 GiB | 76.4% | −3.2 | 19.9 px |
| keep_attn | 3.7 GB | 7.2 GiB | 70.0% | −9.7 | 35.5 px |
| keep_deep（24–35 层全保） | 4.5 GB | 7.2 GiB | 67.4% | −12.3 | 46.1 px |
| keep_mlp_down | 4.3 GB | 7.2 GiB | 64.0% | −15.6 | 57.4 px |
| V0 全 int4 | 3.2 GB | 6.0 GiB | 67.7% | −11.9 | 44.3 px |

按"每 GB 换回多少点"算（相对 V0 的 67.7%）：

| 保护对象 | 增量显存 | 换回 | 效率 |
|---|---:|---:|---:|
| gate_up FP16 | +2.5 GB | +8.7 点 | 3.5 点/GB |
| attention FP16 | +0.5 GB | +2.2 点（不显著） | 4.4 点/GB |
| 24–35 深层 FP16 | +1.4 GB | −0.3 点 | 负 |
| down_proj FP16 | +1.1 GB | −3.7 点 | 负 |

**部署结论**：预算 <4 GB 时，全 int4（3.2 GB / 67.7%）就是最优，没有便宜的补救；
预算能到 5.7 GB 时，`keep_mlp_gateup`（76.4%）比 V0 多 8.7 点，是这条曲线上
唯一划算的中间点。**"按参数量分配位宽"是错的，必须按模块在计算图里的位置分配。**

### 12.6 把速度与显存也放进同一张表

精度之外，部署真正付的代价是**最低显存预算**和**吞吐**。两者都必须在同一把尺下量
（本项目在这里又踩了一次口径污染，见 `docs/06-error-log.md` 第 40 条）：

| 档位 | 权重体积 | **最低显存预算** | 准确率 | TTFT p50 | TPOT p50 | 吞吐 tok/s |
|---|---:|---:|---:|---:|---:|---:|
| BF16 基座 | 7.1 GB | **12.0 GiB** | 79.7% | 1149 ms | 85.0 ms | 31.9 |
| keep_mlp | 6.5 GB | 9.6 GiB | 78.7% | 677 ms | 99.6 ms | 32.1 |
| keep_mlp_gateup | 5.7 GB | 8.4 GiB | **76.4%** | 691 ms | 103.3 ms | 31.0 |
| keep_attn | 3.7 GB | 7.2 GiB | 70.0% | 696 ms | 102.8 ms | 31.4 |
| keep_deep（24–35 层） | 4.5 GB | 7.2 GiB | 67.4% | — | — | — |
| keep_mlp_down | 4.3 GB | 7.2 GiB | 64.0% | — | — | — |
| V0：全 int4 | 3.2 GB | **6.0 GiB** | 67.7% | 810 ms | 100.5 ms | 31.6 |

> 最低预算的探针只看健康检查，所以对最小值（V0 @ 0.25）额外做了**真实推理验证**：
> 8/8 成功，单条延迟 0.6–7.6 s（KV cache 被压得极小，个别请求要排队）。
> 也就是说 6.0 GiB 是真能跑活的数字，不只是"进程起得来"。

压测条件：1264px 图 / max_tokens 32 / 并发 4 / 64 请求 / 4 预热，
`max_model_len 16384 + enforce_eager + 关闭 prefix caching`，五档完全一致
（`scripts/10_mp_bench.sh`、`scripts/11_min_vram.sh`）。

两条读数：

1. **4bit 把最低预算砍掉一半**（12.0 → 6.0 GiB），这是它唯一确定买到的东西。
2. **4bit 不提速**：TTFT 从 1149 ms 降到 ~700–810 ms（权重读取变便宜），
   但 TPOT 从 85 ms 涨到 ~100 ms（每步要把 4bit 权重解包回 16bit），
   **吞吐五档全部落在 31.0–32.1 tok/s**，统计上无差别。
   混合位宽不改变这个结论 —— 保多少 FP16 都不影响吞吐。
3. 精度-显存曲线上唯一划算的中间点是 `keep_mlp_gateup`：
   比全 int4 多 2.4 GiB 预算换 8.7 个点。

### 12.7 细化量化粒度（group_size 128 → 64）：权重更准，任务更差

12.6 留下的问题是"能不能用比 FP16 更便宜的方式把 8.7 点拿回来"。最自然的候选是
**把量化粒度改细**：权重仍是 4bit，只有 scale 存储翻倍（2775M 参 / 64 个一组，
约 **+0.05 GB**，比保 FP16 便宜 50 倍）。

实测（`--group-size 64`，其余与 V0 完全一致，量化超参逐字段自检通过）：

| 档位 | 权重体积 | 准确率 | 相对 V0 | p（vs V0） | 偏移 p50 | 解析失败 |
|---|---:|---:|---:|---:|---:|---:|
| V0（group 128） | 3.2 GB | 67.7% | — | — | 44.3 px | 12 |
| **g64（group 64）** | **3.3 GB** | **63.9%** | **−3.8** | **0.044** | 54.0 px | 0 |

**细化粒度反而掉 3.8 个点**，且这个方向是反直觉的 —— 所以先做了两步归因，
而不是直接把它写成结论：

**第一步：排除"权重没量化好"。** 用官方 `unpack_from_int32` 解量化两份产物，
和 BF16 原权重比相对误差：

| 模块 | V0 (g128) | g64 |
|---|---:|---:|
| layers.0.mlp.gate_proj | 11.51% | **10.61%** |
| layers.0.mlp.down_proj | — | 更小 |
| layers.17.mlp.gate_proj | — | 更小 |
| layers.35.self_attn.q_proj | — | 更小 |

g64 在**每一个**探针上误差都更小 —— 量化本身是按理论走的，没问题。

**第二步：排除"推理内核"。** vLLM 0.8.5 的 Marlin 支持 group_size 64
（`MARLIN_SUPPORTED_GROUP_SIZES = [-1, 32, 64, 128]`），但"支持"不等于"正确"。
于是把 g64 的权重量化解量化回 BF16（`scripts/12_dequant_export.py`，
252 个张量解量化 + 572 个原样），用一个完全不碰 Marlin 的普通 BF16 路径再评一遍：

| 路径 | 准确率 |
|---|---:|
| g64 原产物（Marlin g64 内核） | 63.9% |
| **同一份权重量化后解量化（普通 BF16 路径）** | **63.7%** |

两者一致 ⇒ **掉点在权重里，不在内核里**。

**真正的机制：AWQ 的缩放搜索是跟着量化网格走的。** 对比两份产物的 LayerNorm
权重（AWQ 把激活感知缩放折叠进前一层 LN，所以 LN 权重的差异就是缩放搜索的差异）：
72 个 LN 里 31.9% 完全相同、中位差异 0.7%，但**layer 6 / 7 / 22 的差异达到
3.91 / 4.44 / 2.48 倍**。也就是说：换了 group_size，AWQ 的 α 搜索在这些层收敛到了
**不同的解**，而新解虽然让权重误差更小，却让任务精度更差。

> **这条比"g64 不行"更有价值**：它说明**权重域的量化误差不是任务精度的预测器**。
> 按权重误差选量化配置会选错 —— 我们按误差挑出了 g64，按任务度量它却是负收益。
> 想真正吃到细粒度的好处，必须让 AWQ 的 α 搜索在新的网格上重做
> （或把 group_size 也纳入搜索目标），而不是只改打包粒度。

**对 Pareto 曲线的影响**：`keep_mlp_gateup`（5.7 GB / 76.4%）仍然是最优中间点；
3.3 GB 这一档不存在"便宜补救"。

### 12.8 仍未回答的

  （在 g64 网格上重搜 α），看能否拿到"3.3 GB / ≥76%"的点。这是把本条负结果
  翻成正结果最直接的一条路。
- 只在 ScreenSpot 上验证；换任务/换模型后"粒度反效"是否仍然成立需重测。


- **更细的量化粒度**：MLP 的 gate_up 用 `group_size=64`（而非 FP16）能换多少点？
