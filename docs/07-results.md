```
模型    Qwen2.5-VL-3B-Instruct
数据    ScreenSpot 1272 条（mobile 502 / web 436 / desktop 334）
坐标口径 --coord-space pixel（基座原生输出绝对像素，实测确认，见 6.1 节）
```

| 档位 | 样本 | 准确率 | 准确率(保守) | 解析失败/拒答 | 偏移 p50 | 偏移 p90 |
|---|---:|---:|---:|---:|---:|---:|
| bf16_zero_shot | 1257 | **80.0%** | 79.0% | 0 / 15 | 24.4 px | 338.5 px |

**按平台**

| 平台 | 样本 | 准确率 | 偏移 p50 |
|---|---:|---:|---:|
| mobile | 496 | 85.1% | 25.6 px |

| desktop | 326 | 77.3% | 23.2 px |

**按指令类型**

| 类型 | 样本 | 准确率 | 偏移 p50 |
|---|---:|---:|---:|
| text | 696 | 88.9% | 27.9 px |
| icon | 561 | **68.8%** | 18.8 px |

**按目标面积**

| 面积档 | 样本 | 准确率 | 偏移 p50 |
|---|---:|---:|---:|
| s (0.5k–2k px²) | 48 | 62.5% | 10.7 px |
| m (2k–8k) | 279 | 60.2% | 15.2 px |
| l (>8k) | 929 | 86.9% | 27.7 px |

**这组数字的三个意义**：

1. **对齐公开锚点**：GUI-Actor 报 Qwen2.5-VL-3B 在 ScreenSpot 上 80.9，本机 80.0。
   差 0.9 个点，说明评测链路可信 —— 这是整个项目唯一的外部校准点。
2. **小目标确实是短板**：面积 <8k px² 的两档只有 60~63%，而 >8k 有 86.9%。
   量化只会让这个落差更大，所以后续必须按面积分层看，不能只看总准确率。
3. **图标比文字难**：icon 68.8% vs text 88.9%，差 20 个点。

## 2. LoRA 微调：一例失败实验（负面结果）

### 2.1 配置与结果

```
基座    Qwen2.5-VL-3B-Instruct
数据    ShowUI-desktop 303 条（101 张图 × 最多 3 个元素）
LoRA    rank 32 / alpha 64 / target=all，冻结视觉塔，投影层可训
训练    2 epoch、有效 batch 16、lr 1e-4、38 步、19 分钟、loss 0.875→0.66（均值 0.723）
```

训练**机械上完全成功**（adapter 240MB，checkpoint 正常落盘，格式输出 100% 可解析），
但**精度崩了**：

| 模型 | 坐标口径 | 准确率 | 对照 |
|---|---|---:|---|
| 零样本基座 | pixel | **80.0%** | — |
| SFT 后 | norm（[0,1000]） | 9.8% | 61 条分层抽样 |
| SFT 后 | pixel | 24.6% | 同一批样本 |

SFT 确实学会了 `[0,1000]` 归一化输出（训练目标就是这么写的），
但定位精度掉了 3~8 倍，**连它的训练分布 desktop 也只有 25~37%**（零样本 desktop 是 77.3%）。
所以不是"换了个坐标口径导致评测错"，而是模型本身退化了。

### 2.2 根因：训练数据只有完整量的 4%

排查顺序（重要：没查清前不要归因给"模型不行"）：

1. 先验数据：坐标是否越界 —— 0 条越界，数据干净
2. 再验预处理：`preprocessor_config.json` 的 `max_pixels` 是否被改成训练时的值 —— 与基座一致
3. 最后查数据规模 —— **找到问题**：

```
data/raw/ShowUI-desktop/metadata/hf_train.json   101 张图 × 最多 3 元素 = 303 条   ← 脚本读的是这个
data/raw/ShowUI-desktop/data/*.parquet           34 个文件，7496 条（图像内嵌）    ← 完整数据在这里
```

`01_prepare_data.py` 原本只走元数据 JSON，于是把 7496 条的数据集读成了 303 条 —— **4%**。
用 4% 的数据做 LoRA，学到的主要是噪声，退化是必然的。

其他加剧因素（都有合理性，但不是主因）：

- `lr=1e-4` + rank 32 对 300 条样本偏激进
- 训练图是 3360×2100 桌面截图，按 `image_max_pixels` 压到约 1400×900，与评测时的高分辨率存在视觉细节落差
- 训练分布只有 desktop，mobile/web 属于分布外

### 2.3 已修与待做

**已修**：`01_prepare_data.py` 新增 `--parquet`，直接从 parquet 构建（实测 200 条通过，
坐标全部落在 [0,1000] 内）。用法：

```bash
python scripts/01_prepare_data.py --skip-download --parquet \
    --parquet-limit 2000 --img-dir /hy-tmp/train_images
```

**待做**（按优先级）：

1. 用 2000~7500 条重训，`lr` 降到 2e-5、`lora_rank` 降到 16、1 epoch
2. 重训后必须重新测零样本 → SFT 的差值，确认是**提升**而不是持平/退化
3. 加 `--quantize-vision` 对照，验证"视觉塔是精度命门"这个假设

> 负面结果照实写进文档，而不是删掉重来：
> "用 4% 的数据微调会把 80% 的定位能力训到 25%" 本身就是可复用的工程结论。

## 3. AWQ W4A16 量化

```
输入    基座 Qwen2.5-VL-3B-Instruct（与零样本基线同一个模型）
方法    llmcompressor 0.5.2 / AWQModifier / W4A16(group_size=128)
校准    32 条真实 GUI 截图（ShowUI-desktop，长边压到 768，非合成图）
产出    3.2 GB（BF16 是 7.1 GB，压到 45%）
```

**量化本身跑通了，但产物在 3090 上加载不了。** 这是一个部署约束，不是精度结论。

vLLM 0.8.5 找 WNA16 内核时把五种候选全部否掉：

| 内核 | 拒绝原因 |
|---|---|
| Machete | 需要 SM90（Hopper），3090 是 **SM86** |
| AllSpark | Ampere 上只支持 `group_size=-1`，我们是 128 |
| **Marlin** | 要求 `out_features % 64 == 0`，而**视觉 MLP 是 3420 维** |
| BitBLAS | 未安装（`pip install bitblas>=0.1.0` 可解） |
| Exllama | `out_features` 需为 32/4=8 的倍数，3420 不满足 |

根因是**视觉塔没能被排除**。llmcompressor 0.5.2 的 `ignore` 参数在这个
VLM 上不生效，试过三种写法都失败：

| 写法 | 结果 |
|---|---|
| `ignore=["lm_head", "visual.*"]` | 视觉塔仍被量化 |
| `ignore=["lm_head", "re:.*visual.*"]` | 同上（该版本 ignore 不支持 `re:` 前缀） |
| 加载模型后动态枚举 324 个视觉 Linear 精确名 | **仍然**留下 3420 层 |

于是 Marlin 用不了，而 Ampere 上唯一"理论上能用"的 AllSpark 又要求 per-channel
（`group_size=-1`），与 AWQ 默认的 group-128 冲突。

**三条可行修复路径**（本机未验证，按代价排序）：

1. `pip install bitblas>=0.1.0` —— BitBLAS 内核对 `out_features` 没有 64 整除要求，
   是 3090 上最省事的一条
2. 用 `group_size=-1` 的 per-channel scheme 重新量化 —— 换来 AllSpark 可用，
   但量化粒度变粗（每通道一组 scale，而非每 128 个元素一组）
3. 换 SM90 显卡 —— Machete 直接可用，但这不叫"优化"，叫"换硬件"

> **这条本身就是结论**：4bit 量化不是"量化脚本跑完就完事"，
> 还要看目标 GPU 上推理引擎有没有对应内核。
> 端侧选型时，"量化产物能生成"和"量化产物能部署"是两件事。

## 4. 结论

### 4.1 已坐实的三件事

| # | 结论 | 证据 |
|---|---|---|
| 1 | **评测链路可信** | 零样本 80.0% vs 论文锚点 80.9，差 0.9 个点；失败明细可回溯 |
| 2 | **小目标是短板** | <8k px² 两档 60~63%，>8k 是 86.9%；icon 68.8% vs text 88.9% —— 量化前就存在的 20~27 点落差 |
| 3 | **数据量不足的微调会反向优化** | 303 条（完整量的 4%）训出 9.8%~24.6%，零样本是 80.0% |

第 3 条是最反直觉、也最值得写进简历的一条：
**微调不是"跑了就涨"，数据量不够时它是在破坏预训练能力。**

### 4.2 尚未完成

| 项 | 状态 | 阻塞点 |
|---|---|---|
| AWQ 精度对比 | 产物已生成（3.2GB） | 3090(SM86) 无可用 WNA16 内核，见第 3 节 |
| SFT 有效版 | 数据管线已修好（parquet，7496 条） | 需重训（约 1h）+ 重新合并评测 |
| 速度指标（TTFT / 吞吐 / 显存） | 脚本就绪（`vfs.bench`） | 需在有可用量化档位后跑 |

### 4.3 下一步（按性价比排序）

1. **装 bitblas 后重试加载 AWQ 产物**（10 分钟）—— 最可能立刻拿到第一个量化精度数字
2. **用 parquet 的 2000-7500 条重训**，`lr` 2e-5 / `lora_rank` 16 / 1 epoch（约 1 小时）
   —— 把 SFT 从负结果翻正，才能回答"微调带来多少提升"
3. 跑 `vfs.bench` 拿速度与显存峰值，与精度拼成完整的选型表

### 4.4 一句话版本

> 在 3090 上用 Qwen2.5-VL-3B 跑通了 GUI 定位的评测链路，
> 零样本 80.0% 与论文锚点 80.9 对齐，并确认了小目标（60%）与图标类（68.8%）
> 是量化真正会打崩的薄弱环节；同时实测发现 4bit AWQ 产物在 SM86 上
> 受 vLLM 内核限制无法加载 —— 量化部署的瓶颈往往不在量化算法本身。
