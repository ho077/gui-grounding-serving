# 设计取舍与改动清单

> 回答三个问题：这个项目**在解决什么**、**相对上游改了什么**、**为什么这么改**。
> 面向两类读者：接手代码的人，以及面试时追问"哪是你做的"的人。
> 结论先行：**上游一行源码都没改，全部通过 CLI 调用；自研的是编排层与测量层。**

---

## 1. 任务定义

**GUI grounding（界面元素定位）**：输入一张界面截图 + 一句自然语言指令，输出目标元素的中心点坐标。

```
输入  截图 + "点搜索框"
输出  {"point": [312, 148]}      归一化到 [0,1000]，评测时按真实分辨率还原
判定  命中 = 预测点落在标注框内
      偏移 = 预测点到标注框中心的像素距离
```

**为什么选这个场景**（三条同时成立才值得做）：

1. **与既有能力同构**——遥感指代分割是「文本指代 → 地物像素」，GUI grounding 是「文本指令 → 元素坐标」，
   共享"视觉语言引导的空间定位"内核。是能力迁移，不是从零学。
2. **端侧叙事天然成立**——手机上跑 GUI agent 必须量化，于是"量化到什么程度还能点准"是真问题，
   整条工程链（微调 → 量化 → 部署 → 压测）全部有了目标，而不是为了跑而跑。
3. **需求真实**——同方向 `UI-TARS-desktop` 39k star。

---

## 2. 验收口径：不刷榜，给边界

**不刷 ScreenSpot 榜单**。那是字节、小米的赛道，个人刷不动；真刷到最优，结论已经可以发论文了，
放在一个 1.5 周的工程项目里反而显得定位不清。

本项目要回答的是一个**工业选型问题**：

> 量化到哪一档开始崩？崩在哪一类样本上？因此什么场景可以用、什么场景不能用。

这类结论有两个特点：刷榜刷不出来；只有把整条链路跑通才拿得到。

## 3. 相对上游的改动

### 3.1 上游依赖与致谢

| 项目 | 角色 | 用法 | 是否改源码 |
|---|---|---|---|
| **LLaMA-Factory** (`hiyouga/LLaMA-Factory`) | 微调引擎 | `llamafactory-cli train` / `export` | **否** |
| **vLLM** (`vllm-project/vllm`) | 推理引擎 | `vllm serve`；官方 `vllm bench serve` 做交叉验证 | **否** |
| **llmcompressor** (Red Hat AI / vLLM 团队) | 量化工具 | AWQ W4A16，输出 compressed-tensors | **否** |
| **vllm-project/recipes** | 方法论文档 | 提供部署与 benchmark 的标准做法 | 无代码依赖 |
| **microsoft/GUI-Actor** (NeurIPS'25) | 参考实现 | 只用它的公开数字做**自检锚点**，不用它的结构 | 否 |

**对外表述**：「基于 LLaMA-Factory + vLLM 搭建端到端流水线，自研了能力检测、压测与质量评测层」。
**不要说**「对 LLaMA-Factory 做了二次开发」——没改过源码，被追问会穿。

### 3.2 训练配置（`configs/sft/qwen25vl_3b_gui_lora_3090.yaml`）

| 项 | 本仓库取值 | 理由 |
|---|---|---|
| `freeze_vision_tower` | `true` | 省约 1.2GB 显存与对应优化器状态；更重要的是**小数据微调把预训练视觉表征带偏是 VLM 微调最常见的事故** |
| `train_mm_proj` | `true` | 投影层必须跟着学，否则跨模态对齐退化 |
| `lora_rank` | 32 | 定位任务比对话任务更吃容量，通用教程常用的 16 偏小 |
| `image_max_pixels` | 1605632（≈1408×1140） | **分辨率是定位任务的命门**。目标可能只有 20×20 px，图压太狠小目标直接消失，会呈现"大元素无损、小元素归零"的假象 |
| 基座 | Qwen2.5-VL-3B | GUI-Actor 给了公开锚点（零样本 80.9 / 25.9）。报出的数偏离太远可立刻自检出评测脚本有问题——这是纠错机制 |

> `freeze_vision_tower` 是一个**可以做的消融**：改成 `false` 重跑对比 offset p50，
> 若结论显著，本身就是 README 里值得写的一节。

### 3.3 部署配置（`configs/serve/*.yaml`）

| 项 | 做法 | 理由 |
|---|---|---|
| `--no-enable-prefix-caching` | 全部档位默认关闭 | vLLM 官方 recipe 明文要求。多数教程不提这条 |
| FP8 档位 | 启动前由 `hardware.py` 判定，3090 上直接 SKIP | 3090 是 Ampere SM 8.6，**不支持 FP8**（需 8.9+）。与其等加载几分钟后报错，不如启动前判掉 |

为什么关闭 prefix caching 这么关键：多模态请求同一张图第二次几乎零 prefill，
TTFT 会好看到失真，**档位之间不可比**。

### 3.4 自研模块（`src/vfs/`）

| 模块 | 干什么 | 相对上游默认 |
|---|---|---|
| `grounding.py` | 定位评测：命中率 + 像素偏移 + 按面积/平台/指令类型分层 | **上游没有**。这是本项目的核心增量 |
| `bench.py` | 自建流式压测，测 TTFT / ITL / TPOT / 吞吐 | 官方工具有，但多模态负载不可控、参数名换过几轮 |
| `hardware.py` | GPU 微架构能力检测，自动跳过不支持的精度档位 | 上游没有 |
| `vram.py` | 后台 NVML 采样**真正的显存峰值** | 常见做法是读测完的残值，不准 |
| `serve.py` | 配置 → vLLM 命令，含启动前兼容性校验 | — |
| `report.py` | 从实测 JSON **自动推出**选型结论并回写 README | 手写结论必然挑好看的写 |

### 3.5 实测踩坑（摘要，完整清单见 `docs/06-error-log.md`）

三处**评测逻辑**错误值得单列，因为它们不报错、只悄悄给错数：

| 问题 | 现象 | 后果 | 修复 |
|---|---|---|---|
| **坐标约定断裂** | 零样本 acc **0.5%**，锚点是 80.9 | 差两个数量级，全盘皆错 | prompt 声明坐标空间 + `point_to_pixels()` + `--coord-space` 三种口径 |
| **`--limit` 抽样退化** | `--limit 200` 全落在 mobile | 分层统计只剩一个平台 | `_stratified_limit()` 按平台比例分摊 |
| **失败样本被排除** | 1272 条只统计 1060 条（16.7%） | 答错的样本被藏起来，准确率虚高约 3 个点 | 区分"格式失败"与"模型拒答"，同时报 `accuracy` 与 `accuracy_strict` |

坐标约定那条最值得一说：Qwen2.5-VL 基座**原生输出绝对像素**，
而训练目标是 [0,1000]、评测也按 [0,1000] 还原 —— 唯独"模型实际输出什么"没人管。
且**给 prompt 补上 [0,1000] 声明后模型照旧输出像素**（同一条样本 `(2408,159)` → `(2413,159)`），
证明这是预训练烧进去的行为，改 prompt 让它听话是行不通的，只能由评测侧显式指定口径。

修复后 **81.0%**，与锚点 80.9 吻合。**锚点数字真的救了这次**：
若没有公开数字作参照，0.5% 会被当成"模型就是不行"写进报告，后面所有档位对比都建在错误地基上。

> 零样本档与 SFT 档口径不同（前者 `pixel`、后者 `[0,1000]`），跨档比较需注明；
> 量化损失的分母仍应是 **SFT 后的 BF16**，零样本只作参考行。

### 3.6 量化（`scripts/04_quantize.py`）

- **校准集用真实 GUI 截图**，不用合成图——缩放因子必须匹配部署分布
- `--quantize-vision` 做成**可选项**：视觉塔要不要量化，对定位任务是关键消融，
  它直接对应"小图标崩塌"这个假设

## 4. 明确不做的事

| 不做 | 原因 |
|---|---|
| 不照搬 GUI-Actor 的 action head | 那是**新增模型结构**，会破坏标准量化部署链路；且引入第二个变量——精度损失到底来自量化还是结构，就说不清了。本项目只保留**量化**这一个变量 |
| 不刷榜单排名 | 见第 2 节 |
| 不做端到端 agent 评测 | 需要真实环境（OSWorld 那一套），成本高且方差大。只做 grounding 静态评测 |

---

## 5. 可信度怎么保证

自建的压测与评测不能自证清白，做了三层：

1. **mock 服务反推计时**：已知行为的 mock（TTFT 200ms / ITL 50ms），实测 201.78ms / 50.67ms，5 项全 PASS
   → `tests/`
2. **与官方 `vllm bench serve` 交叉验证** → `scripts/06_bench_official.sh`
3. **公开数字锚点**：GUI-Actor 报的 Qwen2.5-VL-3B 零样本数，用于自检评测脚本是否正确

评测逻辑另有 20 项自检（`tests/test_grounding.py`），覆盖坐标解析含格式走形、归一化还原、命中判定、端到端 mock 反推。

## 6. 一句话版本（面试用）

> 以 GUI 元素定位为落地场景，用 LLaMA-Factory 做 LoRA 微调、llmcompressor 做 AWQ 量化、
> vLLM 做部署，自研了一套精度与速度的联合评测：除了准确率还统计坐标像素偏移并按元素面积分层，
> 因为量化损伤先表现为坐标漂移但仍命中，只看准确率会误判为无损。
> 目标是给出"量化到哪一档、在哪类元素上开始不可用"的边界，不是刷榜。
