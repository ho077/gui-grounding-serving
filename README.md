# gui-grounding-serving

**Qwen2.5-VL-3B 的 GUI 元素定位：微调 → 量化 → vLLM 部署 → 精度与速度联合评测。**

```
  截图 + 指令  ->  定位元素坐标  ->  LoRA 微调  ->  AWQ 量化  ->  vLLM 部署  ->  分层评测
                                                                                 ├─ 准确率
                                                                                 ├─ 坐标偏移 px
                                                                                 └─ 按面积/平台分层
```

---

## Motivation：只报准确率是不够的

GUI agent 能不能用，第一步取决于 **grounding**——把「点击设置图标」这句话落到屏幕上正确的位置。
定位不准，后面再多步规划也全崩。

端侧部署必须量化。但量化到底把定位精度压坏了多少？现有工作几乎只报**准确率**，
而准确率是**二值**的：预测点落在 GT 框内就是 1，否则 0。

问题在于量化损伤是**渐进**的：权重压低比特后，坐标往往先开始「飘」，
但还落在框内——此时准确率纹丝不动，看起来「INT4 无损」。
等指标突然掉下来时，已经越界了。

**所以这里额外统计预测点到 GT 框中心的像素偏移。**
准确率不变而偏移增大 = 已经在退化，只是还没越界。这是判断「能不能上 INT4」的主要依据。

---

## Method

| 环节 | 做法 |
|---|---|
| 微调 | LoRA（rank 32）SFT，输出归一化到 `[0,1000]` 的坐标 JSON |
| 合并 | LoRA 合并回基座，得到标准模型目录（QLoRA adapter 不能直接量化，会报 dtype 不匹配） |
| 量化 | AWQ W4A16（`llmcompressor`），校准集用**真实截图** |
| 部署 | vLLM，OpenAI 兼容接口 |
| 评测 | 准确率 + 偏移 p50/p90 + 按**元素面积 / 平台 / 指令类型**分层 |
| 速度 | 自建流式压测，测 TTFT / TPOT / 吞吐 / 显存峰值 |

分层是核心：小图标和大按钮对量化的敏感度差一个量级，
平均下来「只掉 3 个点」可能掩盖掉「小图标掉 11 个点」。

### 分辨率阶梯（**全量 1272 条**，三者同源后才可信）

前置条件：**客户端缩放 + GT 框同比缩放 + 显式 `--coord-space pixel`**，缺一个就是另一道题。

| 长边上限 | 平均视觉 token | 400 子集 | **全量 1272** | 拒答数 | 相对原图（全量） |
|---|---:|---:|---:|---:|---|
| **1280** | 1046 | 82.9% | **80.6%** | 28 | **+0.6（噪声内，持平）** |
| 1024 | 719 | 81.3% | 75.5% | 33 | **−4.5 点** |
| 768 | 415 | 72.9% | — | — | −8.5（子集口径） |
| 512 | 184 | 46.2% | — | — | −35.2（子集口径） |
| 原分辨率（≤12.8M px） | 3175 | 81.4% | 80.0% | 15 | 基准 |

> ⚠️ **子集曾经给出错误答案**：同一份 400 条子集上 1024 / 1280 / 原图三者是
> 81.3% / 82.9% / 81.4%，看着完全不可区分，于是写下了"平台区 1024~1280"这个结论。
> 全量复核后是 **80.6% / 75.5% / 80.0%** —— 1280 确实持平，但 **1024 掉 4.5 点**。
> 根因是 31% 的子集引入了抽样偏差（详见 `docs/06-error-log.md` 第 35 条）：
> 分层结果方向对、幅度错，只看 m 桶（63.5%→84.5%）会以为整体验证通过了。
> **规矩：子集只能筛掉明显不可能的选项，"持平/无损"这类断言必须在全量上说。**

> 结论：**拐点是 1280，不是 1024**。压到长边 1280，视觉 token 从 3175 降到
> **1046（−3.0 倍）**而精度与原分辨率持平（80.6% vs 80.0%，1σ≈2 点）；
> 再往下到 1024（719 token）就要付 4.5 个点。
> 这条可以直接落地：**端侧第一步应该是缩到 1280 而不是保原分辨率**，
> 真正的精度成本在后面的量化。

### 与公开工作的对比（检索于 2026-10，详见 [docs/07-results.md](docs/07-results.md) 第 7 节）

| 维度 | 我们的结果 | 公开水平 |
|---|---|---|
| 零样本精度（ScreenSpot，3B） | **80.0%** | GUI-Actor 报同一模型 80.9；SOTA ≈94.7（GUIrilla-See-7B） |
| 换 SOTA 权重（Jedi-3B，官方协议） | **82.0%**（+2.0） | 论文报 88.6；我们受 1.8M px 输入上限约束，未复现到论文口径 |
| 微调（3B） | 62.7%（负结果） | Jedi-3B 88.6 / GUI-Actor-3B 91.0，但都用 3M+ 样本 |
| **分辨率 vs 比特** | **缩到长边 1280 是免费的（token −3.0×）；4bit 才要付真金白银** | 多篇论文证明"分辨率重要"，但**无人把它与压比特放在同一把尺、且在同一份全集上比过** |
| 4bit 速度 | TPOT +7.8%，三档并发无反超 | Cider SDK 独立测出 W4A16 瓶颈在激活读取、W8A8 快 1.4~2.2× |

两个值得注意的检索发现：

1. **同一个模型的公开数字能差 40 个点** —— Qwen2.5-VL-3B 在 ScreenSpot-v2 上有
   39.1 / 46.9 / 80.9 三种公开值。我们实测 80.0 与 GUI-Actor 的 80.9 对齐，
   说明口径一致；跨论文比数字意义有限。
2. **结论要有外部锚点**：本项目推翻自己两个数字的那次排查（见下）根因是
   "只做内部自洽校验"。现在凡是压分辨率的实验，**必须先解释平台分布**
   （谁被缩放了、谁没有），否则不采信。

**四条实测结论（第 1 条已订正）**：

1. **~~压分辨率比压比特贵得多~~ → 订正为：resize 到长边 1280 是免费的，真正的成本是量化**
   —— 全量 1272 条上，长边 **1280** 与原分辨率**持平**（80.6% vs 80.0%，1σ≈2 点），
   视觉 token 少 **3.0 倍**；1024 才开始掉（−4.5 点）。
   ~~同一输入口径下 4bit AWQ 要掉 12~16 点（长边 1600：80.5% → 64.0%）~~
   ⚠️ 这一组也含尺度污染（`docs/06-error-log.md` 第 36 条）：1600 的近正方形图
   会被服务端二次 resize。干净口径（1024）下损失是 **11.2 点**，
   正在按 1264 口径重测，见 `scripts/09_mp_sweep.sh`。
   旧结论"−59.7 点"与"−3.5 点"均为测量口径污染，不是模型行为。
2. **4bit 换不来速度，只换得来显存** —— TPOT 反涨 7.8%（W4A16 每步要把 4bit 权重
   解包回 16bit，且该档位必须 `enforce_eager`）。它真正买到的是把"塞不进 10.8GB"
   变成"只占 8.7 GiB"。代价现在量清楚了：**12~16 个点**，这个价要在显存预算里衡量。
3. **微调是负结果** —— 四轮实验（数据量、lr/rank、训练目标口径、补网页数据）
   最好的一版 62.7%，仍比零样本低 17.3 个点。瓶颈是底图多样性（1600 条只来自 101 张桌面截图）。
4. **换权重是唯一涨点的路** —— Jedi-3B（NeurIPS'25）用官方协议跑到 82.0%，
   比基座高 2.0 点、偏移 p50 从 24.4 px 降到 **8.6 px**（定位更"稳"，不只是分高）。
   未达到论文 88.6：本机该 checkpoint 输入超过约 1.9M px 时 vLLM 0.8.5 会挂死，
   只能用 ≤1.8M px 口径。

> **量化对比的口径**：本节所有量化数字都在"客户端缩放 + GT 同比缩放 + `--coord-space pixel`"
> 三同源前提下取得（脚本：`scripts/06_ladder.sh`）。AWQ 档仍受 vLLM 0.8.5 的
> dummy profiling 限制无法在原分辨率服务，这是已知局限，见
> [docs/07-results.md](docs/07-results.md) §11.2。

**测试条件**：Qwen2.5-VL-3B · RTX 3090 24GB · ScreenSpot · max_tokens=32
· 关闭 prefix caching · 4 请求预热

**已测部分的口径**：ScreenSpot 1272 条（mobile 502 / web 436 / desktop 334）；
坐标口径 `--coord-space pixel`（基座原生输出绝对像素，实测确认）；

| Jedi = **11.0%** | `jedi_3b` | `--max-side` 缩图后 GT 没跟着缩，`xywh` 被误判成 `xyxy` | 官方协议：**82.0%**（`jedi_official`） |

否则测到的是缩放链路的误差，不是模型能力。完整排查过程在
[docs/07-results.md](docs/07-results.md) §11 与 [docs/06-error-log.md](docs/06-error-log.md) 第 34 条。

## 快速开始

无 GPU 也能跑的部分（环境自检、评测逻辑校验）：

```bash
make install
make hardware     # 看看这台机器支持哪些精度档位
make test         # 校验评测与压测的判定逻辑
```

云端（RTX 3090 24GB）完整流程：

```bash
pip install -r requirements-train.txt
make pipeline     # data → train → merge → quantize → scan → report
```

单步执行见 `make help`。

| SFT v4 = 59.4% | `make data-web && make train && make merge` 后评测 | 59.4% |
| 速度/显存 | 起服务后 `make bench` | TTFT p50 ≈1.1s，吞吐 ≈44.8 tok/s |

**必须先满足的三条硬性前提**，否则数字一定对不上：

1. **评测必须显式加 `--coord-space pixel`**。基座原生输出绝对像素，
   而 `auto` 会把 desktop 上常见的 923 这类值误判成 [0,1000] 归一化，
   准确率直接掉 20+ 个点（`docs/06-error-log.md` 第 4 条）。
2. **AWQ 产物必须过一遍 ignore 命名修复**。llmcompressor 把 ignore 写成
   `model.visual.*`，而权重键是 `visual.*`，vLLM 一条都匹配不上，会误判
   视觉塔被量化并拒绝加载。`make quantize` 已内置该修复，
   也可单独跑 `python scripts/fix_awq_ignore.py <模型目录>` 自检。
3. **缩放必须客户端做，且 GT 跟着缩**（这是 2026-10-19 订正的那一坑）。
   只要在**服务端**降采样（`--mm-processor-kwargs max_pixels`）而 GT 不缩，
   就会测到"缩放链路的系统性偏移"而不是模型能力 —— 且因为 dataset 里
   desktop 只有 35% 的图超过 1.6M px、mobile/web 是 100%，
   它会伪装成"desktop 还行、mobile/web 崩了"的平台差异。
   `scripts/06_ladder.sh` 里的做法可以照抄；核查脚本：`src/vfs/grounding.py`
   的 `_xywh_to_xyxy` 已加"缩放前后相对坐标偏差必须为 0"的自检。

> **已知局限**：AWQ 档位受 vLLM 0.8.5 的 dummy-input profiling 限制，
> `max_pixels` 只能钉在约 1.6M 才能起服务。因此量化对比是在
> **客户端长边 1512/1600**（服务端 resize 为空操作）这一口径下做的，
> 两侧模型走的是同一条链路，可比；代价是没有"原分辨率 + 4bit"这一格。
> 详见 [docs/07-results.md](docs/07-results.md) §11.2。

## 关键决策

### 1. 先查硬件能力，再决定跑哪些档位

精度能不能用取决于 GPU 微架构，不是取决于你想不想用：

| GPU | 架构 | FP8 | NVFP4 |
|---|---|---|---|
| RTX 3090 | Ampere SM 8.6 | ❌ | ❌ |
| RTX 4090 / L40 | Ada SM 8.9 | ✅ | ❌ |
| RTX 50xx | Blackwell SM 12.0 | ✅ | ✅ |

3090 上照抄 FP8 配置，vLLM 要等到权重加载阶段才报错。
`src/vfs/hardware.py` 在**启动前**就剔除不可用的档位。

### 2. 视觉塔量不量化，做消融而不是拍脑袋

默认跳过 `visual.*`，只压语言部分——定位精度主要由视觉编码器决定，压它风险最大。
但这不能只凭直觉。用 `--quantize-vision` 跑对照实验，
比较「显存省了多少」vs「偏移涨了多少」，结论才站得住。

### 3. 校准集必须用真实截图

校准数据决定每层的激活缩放因子。用合成图校准，缩放因子与真实分布不匹配，
量化误差会被放大。这里直接从训练集采样真实截图。

### 4. Benchmark 必须关闭 prefix caching

vLLM 官方 recipe 明文要求，多数教程不提。
不关的话重复截图第二次几乎零 prefill，TTFT 好看到失真，档位间不可比。

### 5. 压测客户端的计时要能自证

自建压测不能自证清白。`tests/` 里用「行为已知」的 mock 服务反推计时，
再用官方 `vllm bench serve` 在真实服务上交叉验证。

### 6. 结论必须有外部锚点，不能只做内部自洽校验

本项目最有价值的一条经验来自一次**自我推翻**：早期"压分辨率 −59.7 点"这个数字看起来很结实，
在三个不同模型档位上都复现出来了（BF16 / AWQ / SFT），内部完全自洽 —— 但它是错的。

它缺的是一个外部锚点。事后看，最省力的校验是**让平台分布能被"谁被缩放了"解释掉**：

| 平台 | 图像 >1.6M px 的比例 | 服务端降采样后的表现 |
|---|---:|---|
| desktop | 35%（p50 1.12M px） | 59.0%（幸存） |
| mobile | **100%**（p50 2.96M px） | 9.7%（崩） |
| web | **100%**（几乎全是 3.69M px） | 2.3%（崩） |

三个截然不同的模型档**崩在同一个地方**，这不可能是巧合 —— 当时就该怀疑链路而不是模型。
现在这条写成硬规矩：**只要看到 desktop 明显好于 mobile/web，先查坐标链路**，
详见 `docs/06-error-log.md` 第 34 条与 `docs/07-results.md` §11。

## 已知限制

- Qwen2.5-VL-3B 版 `template` 为 `qwen2_vl`；换模型需同步改配置与坐标解析
- `freeze_vision_tower=true` 默认开启，可作为消融项关闭重跑
- 3090 无 FP8，`configs/serve/fp8.yaml` 会被自动跳过
- ScreenSpot-Pro 需 `--with-pro` 额外下载，分辨率更高、显存压力更大
- **没有"原分辨率 + 4bit"这一格**：AWQ 档受 vLLM 0.8.5 dummy profiling 限制只能跑
  ≤1.6M px；量化对比统一在客户端长边 1512/1600 这一口径下做
- **Jedi-3B 只测到 ≤1.8M px 口径**：输入 ≥约 1.9M px 时该 checkpoint 在 vLLM 0.8.5
  上会挂死（不报错，`docs/06-error-log.md` 第 33 条），因此没能复现论文的 88.6
- 阶梯的 400 条子集只用于**档位之间**互比；与全量 1272 条的数字不可直接相减
  （平台构成不同，差约 ±3 点）
